## 1. 교재의 기본 방향

이 교재는 강사가 앞에서 설명하고 끝나는 강의안이 아니라, 직원이 혼자 보고 따라가며 작은 프로젝트를 끝낼 수 있는 자율학습형 워크북이다.

핵심 메시지는 다음과 같다.

> AI를 잘 쓴다는 것은 완성된 프롬프트를 외우는 것이 아니라,  
> AI와 대화하면서 업무 맥락, 조건, 판단 기준을 함께 만들고,  
> 한 번 해낸 일을 다음에도 재현할 수 있게 절차로 남기는 것이다.

따라서 `Skill 만들기`는 출발점이 아니다. 먼저 실제 문제를 풀고, 시행착오를 겪고, 검수 기준을 세운 뒤, 마지막에 그 절차를 `SKILL.md`로 남긴다.

처음에는 Codex Desktop으로 시작한다. CLI, MCP, Playwright 같은 말은 필요한 순간에만 등장시킨다. 직원이 먼저 익혀야 할 것은 도구 이름이 아니라, 공개 가능한 자료를 주고, 작업을 맡기고, 결과를 확인하고, 다음에 반복할 수 있게 남기는 흐름이다.

## 2. 프롬프트를 다루는 방식

이 교재는 "좋은 프롬프트 모음집"이 아니다. 직원에게 긴 문장을 완성해서 넣어야 AI가 일을 잘한다고 가르치면 안 된다.

이 교재에서 프롬프트 예시는 정답 문장이 아니라 대화 시작문이다. 사용자는 처음부터 모든 조건을 완벽하게 쓰지 않아도 된다. 오히려 Codex에게 먼저 물어볼 수 있어야 한다.

예를 들면 다음과 같다.

```text
이 일을 하려면 네가 무엇을 알아야 해?
보통 이런 자료는 어떤 기준으로 검토해?
내가 놓치기 쉬운 조건이 뭐야?
먼저 작업계획을 세워보고, 내가 확인한 뒤 진행하자.
```

좋은 활용은 한 번의 완성형 지시로 끝나지 않는다. 대화가 쌓이면서 Codex가 사용자의 업무 맥락을 이해하고, 사용자는 결과를 보며 조건을 보완한다. 따라서 각 장의 예시 문장은 그대로 외우는 문장이 아니라, 대화를 시작하고 조정하는 방법으로 읽는다.

## 3. 각 장의 표준 구성

각 장은 같은 흐름으로 쓴다. 직원이 앞 장을 다 잊어도 이 구조만 보고 다시 진행할 수 있어야 한다.

1. 이 장에서 만들 결과물
2. 왜 이 작업이 필요한가
3. 준비물
4. AI에게 먼저 물어보기
5. 조건과 기준을 같이 정하기
6. 작업 맡기기
7. 막혔을 때 점검할 것
8. 결과물 검수하기
9. 혼자 해보는 과제
10. 오늘 배운 절차 정리
11. 다음에도 하게 만들기: Skill 메모

`실패와 검수`는 별도 장으로 두지 않는다. AI 활용에서 검수는 마지막에 한 번 배우는 단원이 아니라 모든 장에 들어가야 하는 습관이다. 각 장마다 "무엇을 믿으면 안 되는가", "어떤 근거를 다시 확인해야 하는가", "어떤 산출물이 나오면 통과인가"를 같이 둔다.

## 5. 차시별 프로젝트 설계

### 00. Codex Desktop 소개와 설치

- 목표: Windows PC에서 Codex Desktop을 설치하고, ChatGPT 계정으로 로그인한 뒤, 공개자료 실습 폴더를 만든다.
- 프로젝트: `codex-public-practice` 폴더를 만들고 Codex에게 폴더 구조와 샘플 파일 하나만 확인하게 한다.
- 제출물: 설치 확인 캡처, 로그인 확인 캡처, 실습 폴더 구조.
- 강조점: 실제 업무폴더 사용 금지, 공개자료/비식별 샘플/가짜 데이터만 사용, CLI는 뒤쪽 선택 과정으로 분리.

### 01. AI에게 일 맡기기

- 목표: AI를 단순 답변자가 아니라 작업자로 이해한다.
- 프로젝트: 여행 또는 출장 일정을 바로 생성하지 않고, 지도/후기/예약/트렌드 자료를 조사한 뒤 일정표를 만든다.
- 제출물: 후보 조사표, 일정표 HTML 또는 Markdown.
- 이유: 처음부터 행정업무로 들어가면 부담이 크므로, 개인비서 감각을 먼저 만든다.
- 검수 기준: 근거 링크가 있는가, 최근 자료인가, 광고성/부정확한 자료를 제외했는가, 일정이 실제 이동 가능한가.

### 02. 공개자료 폴더 읽히기

- 목표: Codex에는 실제 업무폴더가 아니라 공개자료, 비식별 샘플, 가짜 데이터만 맡겨야 함을 익힌다.
- 프로젝트: 공개자료 샘플 폴더의 파일명, 확장자, 수정일, 용도를 표로 정리한다.
- 제출물: 파일 인벤토리 표.
- 검수 기준: 공개자료만 사용, 원본 삭제 금지, 경로 표시, 파일 용도 추정과 사실 구분.

### 03. 문서 정리하기

- 목표: AI에게 명단을 정리하게 하되, 정렬 기준을 함께 확인하는 법을 익힌다.
- 프로젝트: 교육대상자 명단을 부서 직제순으로 정리한다.
- 제출물: 직제순 정리 CSV, 부서별 Markdown 표, 정리기준 확인메모.
- 배울 점: 직제순은 AI가 알아서 맞히면 안 된다. 부서 순서 기준표를 주고, 기준표에 없는 부서는 확인필요로 남겨야 한다.

### 04. Browser Use: 웹브라우저 조사와 자동화

- 목표: Browser Use가 단순 검색이 아니라 웹 화면을 같이 보며 처리하는 방식임을 이해한다.
- 프로젝트: 예약 취소 경로 확인, 멤버십 해지 방법 확인, 서버 설정 보조 같은 시연 사례를 보고, 실습은 공개 웹사이트 조사로 진행한다.
- 제출물: 작업 체크리스트, 근거 링크표, 캡처 폴더, `results.csv`.
- 배울 점: 한 번 보고 판단할 일은 Browser Use로 충분하고, 여러 번 반복할 일은 Playwright로 자동화한다.
- 안전 기준: 내부 시스템 계정, 행정망, 개인정보 포함 화면은 사용하지 않는다. 예약 취소, 결제, 서버 삭제, 권한 변경 같은 최종 버튼은 사람이 직접 판단하고 누른다.

### 05. HTML 보고서 만들기

- 목표: AI가 만든 결과를 브라우저에서 보기 좋은 업무 공유물로 조립한다.
- 프로젝트: 조사 결과, 표, 캡처 이미지를 하나의 HTML 보고서로 만든다.
- 제출물: HTML 보고서.
- 검수 기준: 제목, 요약, 표, 근거, 캡처, 확인일이 있어야 한다.

### 06. 공개 Skill 찾아 사용하기

- 목표: skills.sh나 GitHub에서 마음에 드는 Skill URL을 복사해 Codex에게 "이거 써볼래?"라고 묻는 가장 쉬운 사용 흐름을 익힌다.
- 프로젝트: YouTube downloader Skill 페이지 URL을 Codex에게 주고, Codex가 용도와 사용 방법을 설명한 뒤 테스트로 실행한다.
- 제출물: `skill_사용메모.md`, `youtube_downloader_실습기록.md`.
- 강조점: 사용자가 설치 명령을 외우거나 GitHub 코드를 먼저 읽을 필요는 없다. URL을 주고 Codex가 설명하고 진행하게 한다. 다만 최종 설치와 실행 전에는 위험한 동작이 없는지만 확인한다.

### 07. Skill로 남기기

- 목표: 한 번 성공한 작업을 다음에도 반복할 수 있게 절차화한다.
- 프로젝트: 앞 장에서 완성한 작업을 `SKILL.md` 초안으로 정리한다.
- 제출물: 내 업무 Skill 초안.
- 대화 시작문:

```text
방금 우리가 완성한 작업을 다음에도 반복할 수 있게 정리하고 싶어.
네가 Skill 초안을 만들려면 무엇을 더 알아야 해?
먼저 발동 조건, 입력자료, 처리 순서, 검수 기준을 질문 목록으로 만들어줘.
```

### 08. 기존 PPTX를 읽혀 `design.md` 만들고 새 PPTX 생성하기

- 목표: 기존 교육 PPTX를 단순히 복사하지 않고, 스타일 규칙으로 추출한 뒤 새 자료에 적용하는 방법을 익힌다.
- 프로젝트: 기존 교육 PPTX 또는 공개 샘플 PPTX를 Codex가 분석하게 하고, 색상/폰트/레이아웃/문장 규칙을 `design.md`로 정리한 뒤 짧은 PPTX를 새로 만든다.
- 제출물: `design.md`, 샘플 PPTX, 검수 메모.
- 배울 점: "서식 참고"는 감으로 비슷하게 만드는 일이 아니라, 표지/도비라/본문 레이아웃, 색상, 폰트, 여백, 한국어 줄바꿈 규칙을 문서화하는 일이다.
- 검수 기준: 폰트가 의도대로 적용됐는가, 같은 어절 안에서 줄바꿈이 생기지 않았는가, 하단 여백이 과하지 않은가, 기존 PPTX의 톤은 살리되 민감한 내용이나 저작권 표시는 제거했는가.

### 09. `/goal`로 메모장 클론 프로젝트 끝까지 밀고 가기

- 목표: 한 번의 질문으로 끝나지 않는 작업을 목표 단위로 맡기고, 구현/빌드/검증/수정까지 이어가는 흐름을 익힌다.
- 프로젝트: Windows 기본 메모장을 참고해 작은 메모장 클론을 만든다. 최소 범위는 새 파일, 열기, 저장, 다른 이름 저장, 찾기, 글자 크기 조정이다.
- 제출물: 실행파일, 간단한 사용설명, 검증로그, 회고.
- 배울 점: 코딩 지식 자체보다 중요한 것은 목표를 잡고, 범위를 줄이고, 결과물을 실행해 보고, 수정 요청을 이어가는 방식이다.
- 검수 기준: 실제로 실행되는가, 파일 저장/열기가 되는가, 오류 상황을 처리하는가, 설치파일 또는 실행파일 위치가 정리되어 있는가.

### 10. Codex로 서버/API 설정 관리하기

- 목표: 사용자가 완성형 프롬프트를 쓰지 않아도, 짧은 말에서 시작해 Codex가 질문하고 사용자가 고르며 API 분석 범위를 맞추는 법을 익힌다.
- 프로젝트: Meta 공식 문서와 개발자센터를 확인해 Instagram/Threads 분석 가능 범위를 나누고, 가능하면 Browser Use나 Playwright로 화면을 보며 테스트 세팅을 진행한다.
- 위치: 04장 Browser Use/Playwright와 같은 맥락의 작업이지만, 입문 단계에서 바로 하기에는 어려워 별도 심화 장으로 분리한다.
- 제출물: `meta_api_가능여부.md`, `.env.example`, `api_test_log.md`, `instagram_threads_분석.html`, `다음번_세팅메모.md`.
- 배울 점: API 설정은 목적이 아니라 반응 추이 분석을 위한 준비 과정이다. 사용자는 "어떤 지표를 볼 수 있는지 네가 설명해줘, 내가 골라볼게"처럼 말하고, Codex가 가능 여부·필요 권한·테스트 방법을 확인하게 한다.
- 안전 기준: 기관 공식 계정, 운영 앱, 액세스 토큰, 앱 시크릿은 실습 문서와 캡처에 남기지 않는다. 실제 권한 신청, 운영 전환, 결제, 삭제는 사용자가 직접 판단한다.

# 00. Codex Desktop 소개와 설치

## 이 장에서 할 일

이 장에서는 Windows PC에 Codex Desktop을 설치하고, 처음 실행해 봅니다.

최종 결과물은 다음 세 가지입니다.

- ChatGPT 계정으로 로그인 완료
- `codex-public-practice` 실습 폴더 생성

이 장의 목표는 거창하지 않습니다. 오늘은 Codex에게 일을 시키기 전, 작업 환경을 준비하는 날입니다.

> Codex는 질문에 답하는 챗봇이 아니라,  
> 내 PC의 안전한 작업공간 안에서  
> 자료를 읽고, 파일을 만들고, 결과물을 검토하는 작업자입니다.

다만 처음부터 실제 업무자료를 맡기지는 않습니다. 이 교재에서는 공개자료, 비식별 샘플자료, 가짜 데이터만 사용합니다.

```text
내가 어떤 자료를 준비해야 해?
보통 이런 작업은 어떤 순서로 진행해?
먼저 질문부터 해줘.
```

이 교재의 예시 문장은 "정답 프롬프트"가 아니라 대화를 시작하는 예시입니다. 실제 작업에서는 Codex의 답을 보고 조건을 고치고, 기준을 보태고, 결과물을 다시 검수하면서 업무 맥락을 같이 만들어갑니다.

## Codex Desktop이 무엇인가요

Codex는 OpenAI의 코딩 에이전트입니다. 원래는 개발자가 코드를 읽고, 수정하고, 테스트하고, 리뷰하는 데 많이 씁니다. 하지만 우리가 이 교재에서 보려는 것은 "코딩" 자체가 아닙니다.

우리가 볼 것은 다음입니다.

- 공개자료 폴더를 읽고 파일 목록 만들기
- 웹을 조사하고 근거 링크 정리하기
- 엑셀 샘플을 검토표로 바꾸기
- HTML 보고서 만들기
- 반복 작업을 절차로 정리하기
- 마지막에 그 절차를 Skill로 남기기

즉 이 수업에서 Codex는 개발도구라기보다, **내가 시킨 일을 작업공간 안에서 처리하는 AI 작업자**입니다.

ChatGPT와 다른 점은 여기에 있습니다.

| 구분 | ChatGPT | Codex Desktop |
| --- | --- | --- |
| 기본 사용 방식 | 대화 중심 | 작업공간 중심 |
| 주로 하는 일 | 답변, 요약, 작성 | 파일 읽기, 수정, 생성, 검토 |
| 결과물 | 대화창의 답변 | 실제 파일, 표, HTML, 스크립트 |
| 작업 단위 | 질문 하나 | 프로젝트 또는 폴더 단위 |
| 주의할 점 | 입력 내용 관리 | 파일 접근 범위와 공개등급 관리 |

## 설치 전에 확인할 것

설치 전에는 세 가지만 확인합니다.

### 1. Windows PC인가요

이 장은 Windows 환경 기준입니다. macOS나 Linux 사용자는 별도 안내가 필요합니다.

### 2. ChatGPT 계정이 있나요

Codex는 ChatGPT 계정으로 로그인합니다. OpenAI Help Center 기준으로 Codex는 ChatGPT Plus, Pro, Business, Enterprise/Edu에서 사용할 수 있고, 2026년 5월 현재 제한 기간 동안 Free와 Go에도 포함되어 있습니다. 단, 사용량 제한은 요금제와 워크스페이스 정책에 따라 다릅니다.

기관이나 회사 계정으로 쓰는 경우에는 관리자 설정에 따라 Codex 사용이 제한될 수 있습니다.

### 3. Microsoft Store를 사용할 수 있나요

Windows용 Codex Desktop은 Microsoft Store에서 설치합니다. Microsoft Store 사용이 막혀 있는 PC라면 기관 보안정책에 따라 설치가 제한될 수 있습니다.

2. 화면에서 `Download Codex` 영역을 찾습니다.
3. `Windows` 버튼을 클릭합니다.
4. Microsoft Store가 열리면 `Codex`를 설치합니다.
5. 설치가 끝나면 시작 메뉴에서 `Codex`를 실행합니다.

## 설치 방법 2: 명령어로 설치하기

Microsoft Store 화면을 직접 열기 어렵거나, 명령어 설치가 편한 환경에서는 `winget`을 사용할 수 있습니다.


직원 교육에서는 Microsoft Store 설치를 기본으로 안내하고, `winget`은 보조 방법으로만 소개하는 편이 좋습니다. 명령어가 익숙하지 않은 직원은 Store 화면에서 설치하는 것이 덜 부담스럽습니다.

## 실습용 폴더 만들기

Codex는 폴더를 중심으로 일합니다. 그래서 처음에는 안전한 실습용 폴더를 하나 만들어야 합니다.

바탕화면이나 문서 폴더에 다음 폴더를 만듭니다.

```text
codex-public-practice/
  00_input/
  01_working/
  02_output/
  99_archive/
```

각 폴더의 역할은 다음과 같습니다.

| 폴더 | 역할 |
| --- | --- |
| `00_input` | 공개자료 또는 가짜 샘플자료를 넣는 곳 |
| `01_working` | Codex가 중간 산출물을 만드는 곳 |
| `02_output` | 최종 결과물을 저장하는 곳 |
| `99_archive` | 이전 실행 결과나 참고자료를 보관하는 곳 |

처음에는 `00_input`에 가짜 파일을 하나만 넣어도 됩니다.

예를 들어 `연습메모.md` 파일을 만들고 다음 내용을 넣습니다.

```markdown
# Codex 첫 실습 메모

이 파일은 Codex 설치 확인을 위한 공개 샘플 파일입니다.

- 실제 업무자료가 아닙니다.
- 개인정보가 없습니다.
- 이 파일을 읽고 요약하는 연습을 합니다.
```

```text
실제 업무자료나 개인정보가 없어 보이는지도 점검해줘.
```

결과가 나오면 이어서 요청합니다.

```text
`00_input/연습메모.md` 파일만 읽고 요약해줘.

주의:
- 다른 파일은 열지 마.
- 파일을 수정하지 마.
- 요약 결과는 대화창에만 보여줘.
```

이 실습이 끝나면 Codex가 다음을 할 수 있다는 것을 확인한 것입니다.

- 폴더 구조를 본다.
- 파일 목록을 정리한다.
- 지정한 파일만 읽는다.
- 요약 결과를 만든다.
- 사용자가 정한 금지사항을 따른다.

[그림 0-9 삽입 제안]  
Codex에 첫 요청을 입력한 화면.  
캡션: "첫 요청은 작고 안전하게 시작합니다. 폴더 구조 확인이 먼저입니다."

[그림 0-10 삽입 제안]  
Codex가 폴더 구조와 파일 목록을 표로 정리한 화면.  
캡션: "Codex가 작업공간을 이해하면 다음 작업을 맡길 수 있습니다."

## 꼭 기억할 안전수칙

Codex Desktop은 내 PC의 작업공간을 다룰 수 있습니다. 그래서 편한 만큼 주의해야 합니다.

### 1. 실제 업무폴더를 바로 열지 않습니다

실습에서는 공개자료, 비식별 샘플자료, 가짜 데이터만 사용합니다.

### 2. 공개 여부가 애매하면 넣지 않습니다

공개자료인지 확신이 없으면 Codex에 넣지 않습니다.

### 3. 개인정보가 들어간 자료는 사용하지 않습니다

이름, 연락처, 주소, 주민등록번호, 계좌번호, 민원내용, 인사정보가 들어간 자료는 실습에 사용하지 않습니다.

### 4. 원본은 건드리지 않습니다

실습 폴더에는 원본이 아니라 복사본이나 가짜 데이터를 넣습니다.

### 5. 처음에는 작은 작업만 시킵니다

처음부터 "다 정리해줘"라고 하지 않습니다. 폴더 목록 확인, 파일 하나 요약처럼 작은 요청부터 시작합니다.

### 6. Full access 모드는 쓰지 않습니다

Windows용 Codex app은 샌드박스와 권한 설정을 지원합니다. 교육에서는 기본 권한을 유지하고, 전체 접근 권한이 필요한 작업은 하지 않습니다.

## 막혔을 때 점검할 것

### 1. Microsoft Store가 열리지 않는 경우

기관 PC에서는 Microsoft Store가 막혀 있을 수 있습니다. 이 경우 개인이 임의로 우회하지 말고 담당자에게 확인합니다.

### 2. 로그인은 됐는데 Codex 사용이 안 되는 경우

요금제, 지역, 워크스페이스 설정, 관리자 권한에 따라 Codex 사용이 제한될 수 있습니다. Business나 Enterprise/Edu 환경에서는 관리자가 Codex Local 또는 관련 권한을 허용해야 할 수 있습니다.

### 3. PowerShell 관련 오류가 나는 경우

명령어 실행 중 PowerShell 실행 정책 오류가 나올 수 있습니다. 이 장에서는 명령어 설치를 필수로 하지 않으므로, Microsoft Store 설치를 우선합니다. 필요한 경우 관리자 또는 담당자와 상의합니다.

### 4. Git, Node.js, Python이 없다고 나오는 경우

처음 교육에서는 필수는 아닙니다. 다만 나중에 HTML 생성, 자동화, Playwright 실습을 하려면 Git, Node.js, Python이 있으면 편합니다. 이 내용은 부록이나 심화 장에서 다룹니다.

# 01. AI에게 일 맡기기

## 이 장에서 만들 결과물

이 장에서는 Codex에게 여행 또는 출장 일정을 맡겨 보고, 그 결과를 보기 좋은 일정표로 정리합니다.

최종 결과물은 다음 둘 중 하나입니다.

- `일정표.md`: 글과 표로 정리된 일정표
- `일정표.html`: 브라우저에서 열어볼 수 있는 일정표

여기서 중요한 것은 여행 자체가 아닙니다. 여행 일정은 누구나 이해하기 쉽기 때문에 첫 예제로 쓰는 것입니다. 이 장의 진짜 목표는 다음 감각을 익히는 데 있습니다.

> AI는 질문에 답하는 도구가 아니라,  
> 내가 가진 자료를 읽고 판단해서 결과물을 만드는 작업자다.

조금 더 정확히 말하면, 이 장에서 경험할 것은 "검색해서 대충 추천해 주는 AI"가 아닙니다. 우리가 원하는 것은 여행 조사 에이전트입니다. 여행 조사 에이전트는 머릿속에 있는 일반 지식으로만 답하지 않습니다. 한국 사람들이 실제로 많이 쓰는 지도, 예약, 후기, 여행 플랫폼을 살펴보고, 최근 후기가 어떤지, 요즘 사람들이 어떤 방식으로 여행하는지, 이동 동선이 실제로 말이 되는지 확인한 뒤 일정을 짭니다.

여기서 중요한 것은 처음부터 완벽한 요청문을 쓰는 능력이 아닙니다. 오히려 이렇게 시작해도 됩니다.

```text
부산 여행 일정을 짜보고 싶은데,
네가 제대로 조사하려면 내가 어떤 조건을 알려줘야 해?
보통 여행 일정 만들 때 무엇을 먼저 확인해?
```

Codex가 필요한 조건을 물어보면, 그때 출발지, 이동수단, 피하고 싶은 것, 예산, 숙소 조건을 하나씩 답하면 됩니다. 대화가 쌓이면서 일정의 기준이 만들어집니다.

업무로 바로 들어가면 부담이 큽니다. 민원, 법령, 보조금, 개인정보 같은 단어가 나오면 처음부터 긴장하게 됩니다. 그래서 먼저 생활형 예제로 시작합니다. 여행 일정, 호텔 예약 조건, 준비물 목록처럼 익숙한 주제를 사용하면 Codex가 어떤 방식으로 일하는지 훨씬 빨리 이해할 수 있습니다.

[그림 1-1 삽입 제안]  
Codex 화면에 "부산 1박 2일 여행 일정을 만들어줘"라고 요청하는 첫 화면.  
캡션: "처음에는 업무가 아니라 생활형 요청으로 시작해도 충분합니다."

## 왜 여행 일정부터 시작하나요

많은 사람이 AI를 처음 쓸 때 이렇게 요청합니다.

```text
부산 여행 일정 짜줘.
```

이 요청도 틀린 것은 아닙니다. 하지만 결과는 대체로 평범합니다. 어디서 본 듯한 관광지 목록이 나오고, 시간표도 대충 맞춰집니다. 실제로 내가 쓰려면 다시 고쳐야 합니다.

Codex에게 일을 맡길 때는 조금 다르게 접근해야 합니다. "정답을 말해줘"가 아니라 "내가 어떤 조건을 말해야 하는지 같이 정리해줘"라고 시작해도 됩니다.

처음에는 이렇게 짧게 말해도 됩니다.

```text
부산 1박 2일 여행 일정을 만들고 싶어.
네가 일정을 제대로 짜려면 나에게 무엇을 물어봐야 해?
```

Codex가 질문한 뒤에는 다음처럼 조건을 보태면 됩니다.

```text
부산 1박 2일 여행 일정을 만들어줘.

조건은 다음과 같아.
- 출발지는 광양이고, 자차로 이동한다고 가정해줘.
- 첫날 오전 10시에 부산 도착, 둘째 날 오후 4시에 부산 출발이야.
- 너무 빡빡한 일정은 싫고, 식사와 이동 시간을 여유 있게 잡아줘.
- 유명 관광지만 나열하지 말고, 실제 동선이 자연스럽게 이어지게 구성해줘.
- 결과는 시간대별 표로 만들고, 마지막에 준비물 체크리스트도 붙여줘.
```

이 대화에서 결국 정리되어야 할 것은 다섯 가지입니다.

1. 목적: 부산 1박 2일 여행 일정 만들기
2. 입력 조건: 출발지, 이동수단, 도착·출발 시간
3. 선호 기준: 빡빡하지 않게, 동선 자연스럽게
4. 산출물 형식: 시간대별 표
5. 추가 산출물: 준비물 체크리스트

업무도 똑같습니다. "검토해줘"라고만 해도 시작은 할 수 있습니다. 다만 곧바로 결과를 받기보다, Codex에게 목적, 입력자료, 판단기준, 산출물 형식을 먼저 질문하게 만드는 편이 좋습니다.

[그림 1-2 삽입 제안]  
나쁜 요청과 좋은 요청을 좌우 비교한 화면.  
왼쪽: "여행 일정 짜줘"  
오른쪽: 조건, 산출물, 검수 기준이 들어간 요청  
캡션: "AI에게 일을 맡길 때는 목적, 조건, 결과물 형식을 같이 줍니다."

## 준비물

이 실습에는 실제 개인정보나 업무자료가 필요하지 않습니다. 아래 내용만 준비하면 됩니다.

- 여행지 또는 출장지 하나
- 일정 기간
- 출발지와 도착 시간
- 꼭 하고 싶은 것 2~3개
- 피하고 싶은 것 1~2개

예제에서는 다음 조건을 사용합니다.

```text
여행지: 부산
기간: 1박 2일
출발지: 광양
이동수단: 자차
성향: 너무 빡빡한 일정은 싫음
관심사: 바다, 음식, 사진 찍기 좋은 장소
피하고 싶은 것: 줄 오래 서는 맛집, 이동시간이 긴 동선
```

## 1단계: 조사 범위를 정하기

여행 에이전트에게 바로 "일정 짜줘"라고 말하면 결과가 얕아집니다. 먼저 어디를 조사해야 하는지 알려주는 편이 좋습니다.

국내 여행 일정을 짠다면 다음처럼 조사 영역을 나눌 수 있습니다.

| 조사 영역 | 확인할 자료 예시 | 확인할 내용 |
| --- | --- | --- |
| 지도와 동선 | 네이버지도, 카카오맵, 티맵 길찾기 | 이동시간, 주차, 주변 동선 |
| 장소 후기 | 네이버지도 리뷰, 카카오맵 리뷰, 블로그 후기 | 최근 평판, 대기시간, 실제 방문자 반응 |
| 숙소와 예약 | 아고다, 여기어때, 네이버, NOL/야놀자, 에어비앤비 | 위치, 가격대, 조식 포함 여부, 취소 조건 |
| 액티비티 | 네이버, 클룩, 마이리얼트립, 트리플 등 | 투어, 체험, 입장권, 예약 필요 여부 |
| 트렌드 | 네이버 블로그, 유튜브, 인스타그램, 카페 후기 | 요즘 많이 가는 코스, 새로 뜨는 장소 |
| 제외 기준 | 광고성 글, 오래된 후기, 동선이 나쁜 장소 | 믿을 수 없는 추천 제거 |

플랫폼 순위는 시기마다 바뀝니다. 그래서 교재에서는 특정 사이트 하나를 정답처럼 외우게 하지 않습니다. 대신 "지도, 후기, 예약, 액티비티, 트렌드"라는 조사 영역을 나누고, 각 영역에서 근거를 확인하게 합니다.

[그림 1-3 삽입 제안]  
Codex에게 "여행 조사 범위를 먼저 정해줘"라고 요청하고, 지도·후기·예약·트렌드 조사표가 생성된 화면.  
캡션: "에이전트에게는 정답을 묻기 전에 조사 범위를 먼저 정하게 합니다."

## 2단계: Codex에게 웹 조사를 맡기기

이제 Codex에게 단순 일정 초안이 아니라, 웹 조사부터 맡깁니다. 아래 문장은 정답 프롬프트가 아니라 대화 시작 예시입니다. 길게 쓰기 어렵다면 첫 두 줄만 말하고, 나머지는 Codex가 질문하게 해도 됩니다.

```text
부산 1박 2일 여행 일정을 만들기 전에 먼저 여행 조사부터 해줘.

조건:
- 출발지는 광양이고 자차로 이동해.
- 첫날 오전 10시에 부산 도착, 둘째 날 오후 4시에 부산 출발이야.
- 너무 빡빡하지 않게, 이동시간과 식사시간을 여유 있게 잡아줘.
- 바다, 음식, 사진 찍기 좋은 장소를 중심으로 구성해줘.
- 줄 오래 서는 맛집이나 이동시간이 너무 긴 동선은 피하고 싶어.

조사 방식:
- 머릿속 지식으로만 추천하지 말고, 실제 웹 자료를 확인해줘.
- 네이버지도 또는 카카오맵에서 장소 후기와 위치를 확인해줘.
- 여행 플랫폼이나 예약 사이트에서 숙소/액티비티/예약 필요 여부를 확인해줘.
- 블로그, 카페, 유튜브, 인스타그램 등에서 최근 후기나 요즘 트렌드를 확인해줘.
- 광고성 글처럼 보이는 자료는 근거로 쓰지 말고 제외해줘.
- 가능하면 최근 1년 이내 후기를 우선해줘.

먼저 만들어야 할 결과물:
- 후보 장소 조사표
- 후보 식당 조사표
- 숙소 또는 숙박 지역 후보
- 요즘 많이 언급되는 여행 키워드
- 제외한 후보와 제외 사유
- 각 항목의 근거 링크
```

처음 나온 결과를 바로 정답으로 보지 마세요. 이 단계의 목표는 완성이 아니라 조사표입니다.

조사표를 받으면 다음 다섯 가지를 먼저 봅니다.

- 근거 링크가 실제로 있는가
- 최근 자료와 오래된 자료가 구분되어 있는가
- 광고성 추천을 걸러냈는가
- 지도상 동선이 자연스러운가
- 내가 말한 조건이 반영되었는가

[그림 1-4 삽입 제안]  
Codex가 만든 후보 장소 조사표 화면.  
장소명, 추천 이유, 최근 후기 요지, 근거 링크, 제외 여부가 보이게 캡처.  
캡션: "에이전트형 작업에서는 일정표보다 조사표가 먼저 나옵니다."

## 3단계: 조사 결과를 기준으로 일정표 만들기

조사표가 어느 정도 정리되면 그때 일정표를 만들게 합니다.

```text
좋아. 방금 조사한 후보를 바탕으로 부산 1박 2일 일정을 짜줘.

일정 작성 기준:
- 근거가 약한 장소는 제외해줘.
- 지도상 동선이 자연스럽지 않으면 제외해줘.
- 하루 핵심 장소는 3곳 이하로 해줘.
- 식사시간은 최소 1시간 20분으로 잡아줘.
- 이동시간은 실제보다 조금 여유 있게 잡아줘.
- "가도 되고 안 가도 되는 후보"는 별도 표로 빼줘.

결과물:
- 1일차, 2일차 시간대별 일정표
- 각 장소를 선택한 이유
- 근거 링크
- 대체 후보
- 예약 또는 사전 확인이 필요한 항목
```

이렇게 하면 일정표가 단순 추천 목록이 아니라 조사 결과를 바탕으로 한 계획이 됩니다.

업무에서도 이 차이가 중요합니다. 공고를 찾을 때도, 법령 근거를 찾을 때도, 민원답변을 검토할 때도 바로 결론부터 쓰면 안 됩니다. 먼저 후보와 근거를 모으고, 그다음 판단해야 합니다.

[그림 1-5 삽입 제안]  
조사표를 바탕으로 시간대별 일정표를 만드는 요청 화면.  
캡션: "조사와 판단을 분리하면 결과물이 훨씬 믿을 만해집니다."

## 4단계: 마음에 안 드는 부분을 다시 지시하기

AI 활용에서 중요한 순간은 첫 답변을 받았을 때가 아닙니다. 마음에 안 드는 부분을 보고 다시 지시하는 순간입니다.

예를 들어 첫 일정이 너무 빡빡하다면 이렇게 말합니다.

```text
일정이 조금 빡빡해 보여.

다음 기준으로 다시 조정해줘.
- 하루에 핵심 장소는 3곳 이하로 줄여줘.
- 식사시간은 최소 1시간 20분으로 잡아줘.
- 이동시간은 실제보다 조금 여유 있게 잡아줘.
- "가도 되고 안 가도 되는 후보"는 별도 표로 빼줘.
```

맛집이 너무 흔하다면 이렇게 지시할 수 있습니다.

```text
식당 추천이 너무 흔한 관광객 코스 같아.

다음 기준으로 다시 골라줘.
- 부산에서 먹는 의미가 있는 음식 위주로 골라줘.
- 광양이나 서울에서도 쉽게 먹을 수 있는 메뉴는 제외해줘.
- 왜 그 지역에서 먹을 만한지 이유를 붙여줘.
- 사진을 찾기 좋은 검색어도 함께 제안해줘.
```

이때 직원들이 배워야 할 것은 "프롬프트를 잘 쓰는 법"이 아닙니다. 더 정확히는 다음입니다.

> 결과를 보고 기준을 세우는 법.

AI가 처음부터 내 마음을 알아서 맞추지는 않습니다. 하지만 사람이 기준을 말해 주면 빠르게 고칩니다. 업무에서도 마찬가지입니다. 민원답변 검토, 보조금 정산 검토, 공모전 스크리닝도 처음부터 완벽하게 나오지 않습니다. 검토 기준을 주고, 빠진 기준을 보완하면서 결과를 만들어 갑니다.

[그림 1-6 삽입 제안]  
첫 결과를 보고 "일정이 빡빡하다", "관광객 코스 같다"라고 재지시하는 화면.  
캡션: "AI 활용의 핵심은 첫 질문보다 두 번째 지시입니다."

## 5단계: 결과물을 파일로 만들기

이제 일정표를 파일로 만들어 봅니다.

조사표를 본 뒤에는 이렇게 이어서 말합니다.

```text
좋아. 이 일정을 내가 나중에 열어볼 수 있게 파일로 만들어줘.

작업:
- `부산_1박2일_일정표.md` 파일을 만들어줘.
- 표가 너무 길어지지 않게 1일차와 2일차를 분리해줘.
- 마지막에는 준비물 체크리스트와 대체 코스를 넣어줘.
- 문장은 너무 들뜨지 않게, 실제 일정표처럼 간결하게 써줘.
```

HTML로 보고 싶다면 이렇게 이어서 말합니다.

```text
방금 만든 일정을 브라우저에서 보기 좋은 HTML 파일로 만들어줘.

요구사항:
- 파일명은 `부산_1박2일_일정표.html`로 해줘.
- 첫 화면에는 여행 개요가 보이게 해줘.
- 1일차와 2일차는 구분이 명확하게 보이게 해줘.
- 시간, 장소, 이유, 이동 메모가 표로 들어가야 해.
- 모바일에서도 글자가 너무 작지 않게 해줘.
```

여기서 HTML은 웹사이트를 만들자는 뜻이 아닙니다. 업무 공유용 문서를 브라우저에서 보기 좋게 만드는 방법입니다. 공고 스크리닝 결과, 법령 근거표, 행사 안내자료, 카드뉴스 원고, 현장점검 결과도 같은 방식으로 만들 수 있습니다.

[그림 1-7 삽입 제안]  
브라우저에서 열린 HTML 일정표 화면.  
캡션: "HTML은 개발자만 쓰는 것이 아니라, 업무 결과물을 보기 좋게 공유하는 형식으로 쓸 수 있습니다."

## 6단계: 업무 예제로 바꿔 생각하기

여행 일정 만들기는 가벼운 예제입니다. 하지만 구조는 그대로 업무에 옮겨갈 수 있습니다.

| 생활형 예제 | 업무형 예제 |
| --- | --- |
| 여행 일정 만들기 | 행사 운영 일정 만들기 |
| 호텔 조식 포함 여부 확인 | 계약서 조건 누락 확인 |
| 현지 음식 추천표 만들기 | 정책공고 대상사업 스크리닝 |
| 여행 준비물 체크리스트 | 회의 준비자료 체크리스트 |
| 여행 결과 HTML 만들기 | 업무 검토결과 HTML 보고서 |

예를 들어 행사 운영 일정으로 바꾸면 요청은 이렇게 됩니다.

```text
직원 AI 교육 행사의 운영 일정을 만들어줘.

조건:
- 교육 시간은 14:00부터 17:00까지야.
- 참석자는 일반 행정직 직원이고, 코딩 경험은 거의 없다고 가정해줘.
- 설치 안내, 실습, 질의응답 시간을 모두 포함해줘.
- 중간에 막히는 사람이 생길 것을 고려해서 여유시간을 넣어줘.

결과물:
- 시간대별 운영표
- 진행자 체크리스트
- 준비물 목록
- 예상 문제와 대응방법
```

이렇게 보면 여행 일정과 행사 운영 일정은 크게 다르지 않습니다. 둘 다 조건을 정리하고, 시간을 배분하고, 누락되면 안 되는 항목을 체크하는 작업입니다.

## 막혔을 때 점검할 것

결과가 마음에 들지 않으면 아래를 확인합니다.

### 1. 조건이 너무 적지 않은가

```text
부산 여행 일정 짜줘.
```

이 요청은 조건이 부족합니다. 도착 시간, 이동수단, 선호, 피하고 싶은 것, 결과물 형식이 빠져 있습니다.

### 2. 결과물 형식을 말했는가

AI는 표, 목록, 보고서, HTML, 체크리스트 중 무엇으로 만들지 스스로 추측합니다. 원하는 형식이 있으면 처음부터 말해야 합니다.

### 3. 조사 출처를 나눴는가

여행 조사라면 지도, 후기, 예약, 트렌드가 서로 다른 역할을 합니다. 한 가지 출처만 보면 결과가 한쪽으로 치우칩니다.

업무 조사도 마찬가지입니다. 법령 검토라면 법령 본문, 질의회신, 유권해석, 판례나 재결례를 구분해야 합니다. 공고 스크리닝이라면 공고문, 첨부파일, 신청서식, FAQ를 따로 확인해야 합니다.

### 4. 검수 기준이 있는가

"좋은 일정"은 사람마다 다릅니다. 이 실습에서는 좋은 일정의 기준을 다음처럼 둡니다.

- 최근 후기와 오래된 후기를 구분할 것
- 광고성 추천은 제외할 것
- 하루 핵심 장소 3곳 이하
- 식사시간 1시간 이상
- 이동 동선이 한 방향으로 이어질 것
- 내가 피하고 싶은 조건을 반영할 것
- 대체 후보를 별도 정리할 것

업무에서도 검수 기준이 필요합니다. "좋은 민원답변", "좋은 공고 스크리닝", "좋은 검토표"는 기준 없이 판단할 수 없습니다.

## 결과물 검수하기

완성된 일정표를 보고 아래 항목을 체크합니다.

| 검수 항목 | 확인 |
| --- | --- |
| 근거 링크가 있는가 | □ |
| 최근 후기와 오래된 후기가 구분되어 있는가 | □ |
| 광고성 글이나 근거 약한 추천을 제외했는가 | □ |
| 도착·출발 시간이 반영되었는가 | □ |
| 이동시간이 너무 촘촘하지 않은가 | □ |
| 식사시간이 충분한가 | □ |
| 내가 말한 관심사가 반영되었는가 | □ |
| 피하고 싶은 조건이 반영되었는가 | □ |
| 대체 코스가 따로 있는가 | □ |
| 나중에 다시 열 수 있는 파일로 저장되었는가 | □ |

[그림 1-8 삽입 제안]  
완성된 일정표 옆에 검수 체크리스트를 놓은 화면.  
캡션: "AI 결과물은 검수표와 함께 볼 때 실제 업무에 쓸 수 있습니다."

## 혼자 해보는 과제

아래 셋 중 하나를 골라 직접 만들어 봅니다.

### 과제 A. 생활형

본인이 가고 싶은 여행지 1곳을 정하고, 1박 2일 일정표를 만듭니다.

제출물:

- `여행지_1박2일_일정표.md` 또는 `여행지_1박2일_일정표.html`

### 과제 B. 업무형

3시간짜리 내부 교육 또는 회의 운영 일정을 만듭니다.

제출물:

- 시간대별 운영표
- 진행자 체크리스트
- 준비물 목록
- 예상 문제와 대응방법

### 과제 C. 개인비서형

예약내역, 메모, 가고 싶은 곳 목록이 흩어져 있다고 가정하고, Codex에게 하나의 일정표로 정리하게 합니다.

제출물:

- 정리된 일정표
- 빠진 정보 목록
- 추가로 확인해야 할 사항

## 오늘 배운 절차 정리

이 장에서 한 일은 다음 순서입니다.

1. 하고 싶은 일을 정했다.
2. 조건을 정리했다.
3. 조사해야 할 출처와 제외 기준을 정했다.
4. Codex에게 웹 조사를 맡겼다.
5. 조사표를 보고 근거가 약한 후보를 걸렀다.
6. 조사 결과를 바탕으로 일정표를 만들었다.
7. 결과를 보고 마음에 안 드는 부분을 다시 지시했다.
8. 최종 결과물을 Markdown 또는 HTML 파일로 만들었다.
9. 검수 체크리스트로 결과를 확인했다.

이 순서는 앞으로 계속 반복됩니다.

문서검토를 할 때도, 웹에서 근거를 찾을 때도, Playwright로 반복 작업을 자동화할 때도 기본 구조는 같습니다.

> 문제를 준다.  
> AI가 조사한다.  
> 사람이 기준을 세운다.  
> 근거가 약한 것을 걸러낸다.  
> 다시 고친다.  
> 결과물을 남긴다.  
> 다음에도 하게 절차를 남긴다.

## 다음에도 하게 만들기: Skill 메모

아직 Skill을 만들 필요는 없습니다. 다만 이 작업을 다음에도 반복하려면 어떤 절차를 남겨야 하는지 메모해 봅니다.

마지막에는 Codex에게 다음 작업을 위해 정리하게 합니다.

```text
방금 우리가 만든 여행/출장 일정표 작업을 다음에도 반복할 수 있게 절차 메모로 정리해줘.

포함할 내용:
- 이 작업이 필요한 상황
- 사용자가 준비해야 할 정보
- Codex에게 처음 요청할 문장
- 결과가 마음에 안 들 때 다시 지시할 기준
- 최종 결과물 형식
- 검수 체크리스트

아직 SKILL.md로 만들지는 말고, 나중에 Skill로 바꿀 수 있는 메모 형태로 작성해줘.
```

여기서 중요한 점이 있습니다.

Skill은 처음부터 만드는 것이 아닙니다. 먼저 한 번 해봅니다. 해보면 막히는 지점이 생깁니다. 그 막힘을 해결하면서 기준이 생깁니다. 그리고 마지막에 그 기준과 절차를 정리한 것이 Skill입니다.

이 장에서는 아직 첫걸음만 뗐습니다. 다음 장부터는 이 감각을 실제 업무자료에 적용해 봅니다.

# 02. 공개자료 폴더 읽히기

## 이 장에서 만들 결과물

이 장에서는 Codex에게 공개등급 자료만 모아 둔 실습 폴더를 읽히고, 그 안에 어떤 파일이 있는지 정리하게 합니다.

최종 결과물은 다음 세 가지입니다.

- `공개자료_파일인벤토리.md`: 파일 목록과 용도 추정표
- `공개자료_작업계획.md`: 이 폴더로 무엇을 할 수 있는지 정리한 계획서
- `정리전_주의사항.md`: 공개등급, 개인정보, 읽으면 안 되는 파일 목록

여기서 중요한 것은 파일 정리가 아닙니다. 이 장의 진짜 목표는 다음 감각을 익히는 데 있습니다.

> AI에게 파일을 맡길 때는  
> 실제 업무폴더를 통째로 읽히는 것이 아니라,  
> 공개 가능한 자료만 따로 모아 안전하게 다뤄야 한다.

많은 사람이 Codex를 처음 쓰면 이렇게 말하고 싶어집니다.

```text
이 업무폴더 좀 보고 정리해줘.
```

이 말은 편하지만 위험합니다. 실제 업무폴더 안에는 비공개 문서, 내부검토 자료, 개인정보, 민원자료, 계약자료, 인사자료가 섞여 있을 수 있습니다. 직원 교육에서는 이런 폴더를 Codex에게 읽히면 안 됩니다.

이 장에서 다루는 것은 실제 업무폴더가 아닙니다. 공개자료만 따로 복사해 만든 실습 폴더입니다.

이 장에서도 완성된 프롬프트를 외울 필요는 없습니다. 먼저 Codex에게 이렇게 물어보는 습관을 만듭니다.

```text
이 폴더를 바로 읽혀도 되는지 모르겠어.
공개자료만 안전하게 다루려면 어떤 순서로 확인해야 해?
파일 내용을 열기 전에 먼저 무엇을 점검해야 해?
```

Codex가 제안한 안전 절차를 보고, 사용자가 공개자료 폴더인지 다시 확인한 뒤 작업을 진행합니다.

[그림 2-1 삽입 제안]  
공개자료 샘플 폴더를 파일 탐색기에서 연 화면.  
캡션: "실습에는 실제 업무폴더가 아니라 공개 가능한 자료만 모은 샘플 폴더를 사용합니다."

## 왜 공개자료만 다루나요

AI에게 일을 맡기려면 입력자료가 필요합니다. 하지만 입력자료라고 해서 아무 자료나 넣어도 되는 것은 아닙니다.

공공기관 업무자료에는 공개등급이 있습니다. 직원 교육에서는 원칙을 단순하게 잡습니다.

> Codex 실습에는 공개자료, 배포자료, 비식별 샘플자료만 사용한다.

다음 자료는 실습에 사용하지 않습니다.

- 비공개 또는 부분공개 문서
- 내부 검토 중인 문서
- 결재 전 초안
- 민원자료
- 인사자료
- 계약·견적·계좌정보가 포함된 자료
- 이름, 연락처, 주소, 주민등록번호, 계좌번호가 들어 있는 명단
- 시스템 화면 캡처 중 계정명이나 내부 URL이 보이는 자료
- 공개 여부를 판단하기 어려운 자료

반대로 다음 자료는 실습에 사용할 수 있습니다.

- 이미 홈페이지에 공개된 공고문
- 공개 배포용 안내문
- 공개 보도자료
- 공개 교육자료
- 공개 법령·조례·지침
- 개인정보를 제거한 샘플 엑셀
- 가짜 데이터로 만든 실습 파일
- 직접 만든 예제 파일

이 장의 핵심은 "내 PC 업무폴더를 읽히는 법"이 아닙니다. 공개 가능한 자료만 따로 모아 안전한 실습 폴더를 만들고, 그 폴더를 구조화하는 법입니다.

## 준비물

실습에서는 실제 업무폴더를 쓰지 않습니다. 공개자료 또는 가짜 샘플자료만 넣은 폴더를 하나 만듭니다.

권장 폴더 구조는 다음과 같습니다.

```text
codex-public-practice/
  00_input/
  01_working/
  02_output/
  99_archive/
```

각 폴더의 역할은 다음과 같습니다.

| 폴더 | 역할 |
| --- | --- |
| `00_input` | 공개자료 또는 비식별 샘플자료를 넣는 곳 |
| `01_working` | Codex가 중간 산출물을 만드는 곳 |
| `02_output` | 최종 결과물을 저장하는 곳 |
| `99_archive` | 이전 실행 결과나 참고자료를 보관하는 곳 |

처음에는 `00_input`에 가짜 샘플 파일을 넣는 것이 좋습니다.

예를 들어 다음처럼 구성할 수 있습니다.

```text
00_input/
  2026_직원AI교육_운영계획_공개용.md
  2026_직원AI교육_참석자명단_가짜샘플.xlsx
  2026_직원AI교육_홍보문안_공개용.txt
  2026_직원AI교육_장소사진_샘플.jpg
  2026_직원AI교육_만족도조사_가짜양식.pdf
```

실제 개인정보가 들어 있는 명단, 민원자료, 인사자료, 계약자료는 넣지 않습니다. "가리면 되겠지"라고 생각하기보다, 교육 실습에서는 처음부터 가짜 데이터를 쓰는 편이 안전합니다.

[그림 2-2 삽입 제안]  
`codex-public-practice` 폴더 안에 `00_input`, `01_working`, `02_output`, `99_archive`가 보이는 화면.  
캡션: "공개자료와 결과물을 분리해 실습용 폴더를 만듭니다."

## 1단계: 파일 내용을 읽기 전에 목록만 보기

처음에는 파일 내용을 읽히지 않습니다. 파일명, 확장자, 크기, 수정일만 보게 합니다.

Codex에게 처음부터 정답을 요구하지 말고, 이렇게 안전 점검부터 시킵니다.

```text
이 공개자료 실습 폴더를 먼저 안전하게 파악해줘.

주의:
- 아직 파일 내용은 열어보지 말고, 파일 목록만 확인해줘.
- 원본 파일은 수정, 이동, 삭제하지 마.
- 파일명, 확장자, 크기, 수정일, 경로를 표로 정리해줘.
- 파일명만 보고 추정한 용도는 "추정"이라고 표시해줘.
- 개인정보, 비공개자료, 내부자료 가능성이 있는 파일은 별도로 표시하고 열람 보류해줘.

결과물:
- `공개자료_파일목록_1차.md`를 만들어줘.
```

이 요청에서 중요한 표현은 두 가지입니다.

```text
아직 파일 내용은 열어보지 말고
```

그리고

```text
개인정보, 비공개자료, 내부자료 가능성이 있는 파일은 열람 보류해줘
```

Codex에게 폴더를 맡길 때 가장 위험한 것은 공개 가능 여부가 불분명한 자료를 무심코 읽히는 것입니다. 그다음으로 위험한 것은 사실과 추정이 섞이는 것입니다. 파일명을 보고 "참석자명단"이라고 추정할 수는 있지만, 실제로 그 안에 무엇이 있는지는 열어보기 전까지 모릅니다.

그래서 반드시 `공개 가능 여부`, `확인된 사실`, `파일명 기준 추정`을 나눠야 합니다.

[그림 2-3 삽입 제안]  
Codex에게 "파일 내용은 열지 말고 목록만 확인해줘"라고 요청하는 화면.  
캡션: "공개자료 폴더를 읽힐 때도 첫 단계는 내용 열람이 아니라 목록 파악입니다."

## 2단계: 파일 인벤토리 만들기

파일 목록이 나오면 한 단계 더 정리합니다. 단순 목록이 아니라 실습에 쓸 수 있는 인벤토리로 바꿉니다.

```text
방금 확인한 파일 목록을 공개자료 인벤토리로 다시 정리해줘.

표 컬럼:
- 번호
- 파일명
- 확장자
- 위치
- 크기
- 수정일
- 공개 가능 여부
- 확인된 사실
- 파일명 기준 용도 추정
- 열람 필요 여부
- 개인정보/비공개자료 가능성
- 다음 조치

주의:
- 확인된 사실과 추정을 섞지 마.
- 공개 여부가 불명확하면 "열람 보류"라고 표시해줘.
- 개인정보나 내부자료 가능성이 있으면 "열람 전 확인 필요"라고 표시해줘.
- 최종본인지 초안인지 파일명만으로 판단하지 말고, 추정으로 표시해줘.

결과물:
- `공개자료_파일인벤토리.md`
```

좋은 인벤토리는 이런 형태입니다.

| 번호 | 파일명 | 확인된 사실 | 용도 추정 | 공개/민감 판단 | 다음 조치 |
| --- | --- | --- | --- | --- | --- |
| 1 | `참석자명단_가짜샘플.xlsx` | Excel 파일 | 참석자 목록 샘플일 가능성 | 가짜 샘플 확인 필요 | 열람 전 샘플 여부 확인 |
| 2 | `운영계획_공개용.md` | Markdown 문서 | 행사 운영계획 공개용 | 공개 가능성 높음 | 내용 읽고 요약 가능 |
| 3 | `만족도조사_가짜양식.pdf` | PDF 파일 | 설문 양식 | 가짜 양식 확인 필요 | 필요 시 텍스트 추출 |

이 표는 단순한 파일 목록이 아닙니다. 앞으로 Codex가 어떤 파일을 읽어도 되는지, 어떤 파일은 열람 보류해야 하는지 판단하는 기준표입니다.

[그림 2-4 삽입 제안]  
파일 인벤토리 표가 생성된 화면.  
캡션: "파일 인벤토리는 AI에게 공개자료 폴더를 인수인계하기 위한 첫 번째 지도입니다."

## 3단계: 공개 확인된 파일만 골라 읽히기

이제 파일 내용을 일부 읽힐 수 있습니다. 하지만 전체를 한 번에 읽히지 않습니다. 먼저 공개 확인된 파일부터 고릅니다.

예를 들어 다음처럼 이어서 말합니다.

```text
파일 인벤토리를 기준으로 공개 확인된 파일만 골라줘.

기준:
- 개인정보, 비공개, 내부검토 자료 가능성이 있는 파일은 제외해줘.
- 이미지 파일은 아직 열지 마.
- PDF는 공개 양식인지 가짜 샘플인지 먼저 판단해줘.
- Markdown, txt 파일은 공개용으로 확인된 경우에만 읽어도 돼.
- Excel 파일은 가짜 샘플 데이터인지 확인하기 전까지 내용 열람을 보류해줘.

결과물:
- 공개 확인되어 읽어도 되는 파일 목록
- 보류할 파일 목록
- 보류 사유
```

그다음 공개 확인된 파일만 지정해서 읽힙니다.

```text
다음 파일만 읽고 요약해줘.

읽을 파일:
- `00_input/2026_직원AI교육_운영계획_공개용.md`
- `00_input/2026_직원AI교육_홍보문안_공개용.txt`

하지 말 것:
- 다른 파일은 열지 마.
- 원본 파일은 수정하지 마.
- 공개 여부가 불명확한 파일은 읽지 마.

결과물:
- 각 파일의 핵심 내용 요약
- 이 폴더가 어떤 실습을 위한 폴더인지 추정
- 추가로 확인해야 할 파일 목록
```

여기서 중요한 것은 "다음 파일만"입니다. 공개자료를 다룰 때도 AI가 마음대로 범위를 넓히지 않도록 해야 합니다.

[그림 2-5 삽입 제안]  
공개 확인된 파일과 보류할 파일이 구분된 표.  
캡션: "모든 파일을 읽히지 말고, 공개 확인된 파일과 보류할 파일을 나눕니다."

## 4단계: 이 폴더로 할 수 있는 작업 찾기

폴더 구조와 일부 내용을 파악했으면, Codex에게 이 폴더로 가능한 작업을 제안하게 합니다.

```text
지금까지 확인한 파일 목록과 읽은 내용을 바탕으로,
이 공개자료 폴더로 할 수 있는 작업을 제안해줘.

제안 형식:
- 작업명
- 필요한 입력파일
- 만들 수 있는 결과물
- 공개자료 사용상 주의할 점
- 난이도
- 먼저 하면 좋은 순서

주의:
- 아직 읽지 않은 파일의 내용은 안다고 말하지 마.
- 파일명만 보고 판단한 내용은 추정이라고 표시해줘.
- 개인정보, 비공개자료 가능성이 있는 작업은 보류 표시해줘.
```

예상 결과는 이런 식입니다.

| 작업명 | 필요한 파일 | 결과물 | 주의할 점 |
| --- | --- | --- | --- |
| 교육 운영계획 요약 | 운영계획 공개용 | 1쪽 요약문 | 공개용 문서인지 확인 |
| 홍보문안 다듬기 | 홍보문안 공개용 txt | 직원 안내문 | 과장 표현 제거 |
| 참석자 명단 점검 | 참석자명단 가짜샘플 Excel | 누락검토표 | 실제 명단 사용 금지 |
| 만족도 조사 양식 정리 | 가짜 PDF 양식 | 설문 문항표 | 공개 샘플 여부 확인 |

이 단계에서 직원들은 중요한 감각을 얻습니다.

> AI에게 "뭘 할 수 있어?"라고 묻기 전에,  
> AI가 볼 수 있는 자료의 공개 범위와 금지사항을 먼저 정해야 한다.

[그림 2-6 삽입 제안]  
Codex가 "이 폴더로 할 수 있는 작업"을 표로 제안한 화면.  
캡션: "공개자료 폴더를 파악하면, 가능한 작업과 주의사항을 함께 도출할 수 있습니다."

## 5단계: 작업계획서 만들기

이제 실제 작업을 시작하기 전에 간단한 작업계획서를 만듭니다.

```text
이 공개자료 폴더를 대상으로 가장 먼저 할 작업을 하나 골라 작업계획서를 만들어줘.

작업계획서에 포함할 내용:
- 작업 목표
- 사용할 파일
- 사용하지 않을 파일
- 공개등급, 개인정보, 민감정보 주의사항
- 작업 순서
- 중간 결과물
- 최종 결과물
- 검수 기준
- 원본 보존 방법

결과물:
- `공개자료_작업계획.md`
```

작업계획서는 길 필요가 없습니다. 하지만 다음 문장이 들어가야 합니다.

```text
실제 업무 원본은 사용하지 않고, 공개자료 또는 비식별 샘플자료만 사용한다. 결과물은 `02_output` 폴더에 새 파일로 저장한다.
```

이 문장은 직원 교육에서 반복해서 보여주는 것이 좋습니다. AI에게 일을 맡기는 것은 편하지만, 공개 여부가 불분명한 자료를 넣으면 안 됩니다.

[그림 2-7 삽입 제안]  
`공개자료_작업계획.md`가 생성된 화면.  
캡션: "작업을 시작하기 전에 공개자료 여부, 입력파일, 금지사항, 결과물을 먼저 정합니다."

## 6단계: 실제 업무 예제로 바꿔 생각하기

이 장의 실습은 단순 파일정리가 아닙니다. 모든 업무 자동화의 시작점입니다. 다만 실제 업무에 적용할 때도 원칙은 같습니다.

> 공개자료, 비식별 샘플, 사용 허가를 받은 자료만 다룬다.

| 공개자료 폴더 읽기에서 배운 것 | 실제 업무에서의 의미 |
| --- | --- |
| 파일 목록 만들기 | 자료 현황 파악 |
| 공개 가능 여부 표시 | 보안 사고 예방 |
| 사실과 추정 구분 | AI 착각 방지 |
| 개인정보 가능성 표시 | 개인정보 사고 예방 |
| 공개 확인 파일과 보류 파일 구분 | 작업 범위 통제 |
| 가능한 작업 제안 | 자동화 과제 발굴 |
| 작업계획서 작성 | AI에게 업무 절차 인수인계 |

예를 들어 부서 제출자료 취합 업무를 실습하려면, 실제 제출자료가 아니라 가짜 파일명과 공개 가능한 샘플 파일로 재현합니다.

```text
이 폴더는 여러 부서가 제출한 행사계획서라고 가정한 샘플 폴더야.

먼저 파일 내용은 열지 말고 파일명만 보고,
부서명, 제출일, 파일형식, 최종본 여부 추정, 누락 가능성을 표로 정리해줘.

그다음 공개 샘플로 확인된 파일과 보류할 파일을 나눠줘.
```

민원답변 검토 업무라면 이렇게 바꿉니다.

```text
이 폴더는 민원답변 검토용 가짜 샘플 폴더야.

먼저 파일 목록만 보고,
민원답변 엑셀, 기준문서, 결과물로 보이는 파일을 구분해줘.

개인정보 가능성이 있는 파일은 내용 열람 전에 표시하고,
실제 개인정보 자료는 사용하지 마.
```

즉, 공개자료 폴더 읽기는 이후 모든 장의 출발점입니다. 문서검토, 웹조사, Playwright 자동화, Skill 만들기 모두 여기서 시작합니다.

## 막혔을 때 점검할 것

### 1. 파일이 너무 많은가

파일이 너무 많으면 처음부터 전체를 읽히지 않습니다. 먼저 상위 폴더만 보고, 그다음 하위 폴더를 나눠서 봅니다.

```text
파일이 많으니 전체 내용을 읽지 말고,
상위 폴더 구조와 폴더별 파일 개수만 먼저 정리해줘.
```

### 2. 공개 여부가 애매한가

공개 여부가 애매하면 읽히지 않습니다. 실습에서는 공개자료 또는 가짜 데이터만 씁니다.

```text
공개 여부가 불명확한 파일은 열람하지 말고,
파일명 기준으로만 보류 사유를 표시해줘.
```

### 3. 개인정보가 섞여 있는가

명단, 신청서, 민원자료, 인사자료, 계좌자료는 실습에 사용하지 않습니다. 가짜 데이터를 쓰는 것이 원칙입니다.

```text
개인정보, 비공개, 내부검토 자료 가능성이 있는 파일은 열람하지 말고,
파일명 기준으로만 위험 가능성을 표시해줘.
```

### 4. 최종본이 무엇인지 모르겠는가

`최종`, `최종2`, `수정`, `제출`, `진짜최종` 같은 파일명은 사람이 봐도 헷갈립니다. Codex에게 최종본을 단정하지 말라고 해야 합니다.

```text
파일명만 보고 최종본을 단정하지 마.
최종본 가능성, 초안 가능성처럼 추정으로만 표시해줘.
```

### 5. HWP, PDF, 이미지 파일이 섞여 있는가

HWP/HWPX, PDF, 이미지 파일은 텍스트 추출이 잘 안 될 수 있습니다. 이때는 바로 내용을 요약하게 하지 말고, 먼저 처리 가능성을 확인하게 합니다.

```text
HWP, PDF, 이미지 파일은 바로 요약하지 말고,
텍스트 추출이 필요한 파일로 분류해줘.
각 파일별로 어떤 방식으로 읽을 수 있을지 제안해줘.
```

### 6. AI가 파일 내용을 안 읽고 아는 척하는가

AI가 파일명만 보고 내용까지 아는 것처럼 말하면 안 됩니다. 이때는 바로 고칩니다.

```text
방금 답변에서 실제로 파일 내용을 읽고 확인한 사실과,
파일명만 보고 추정한 내용을 분리해서 다시 써줘.
```

## 혼자 해보는 과제

### 과제 A. 생활형

공개해도 되는 샘플 사진 폴더의 복사본을 만들어 파일 목록을 정리합니다.

제출물:

- 사진 파일 인벤토리
- 중복 또는 이름이 애매한 파일 목록
- 정리 계획

주의:

- 실제 원본 사진 폴더가 아니라 복사본으로 합니다.
- 얼굴, 차량번호, 위치정보 등 개인정보가 보이는 사진은 사용하지 않습니다.

### 과제 B. 공개자료형

공개자료 또는 가짜 데이터로 샘플 행사 폴더를 만들어 파일 인벤토리를 작성합니다.

제출물:

- 파일 인벤토리
- 공개 확인된 파일과 보류할 파일 목록
- 첫 번째 작업계획서

### 과제 C. 취합형

여러 부서가 제출한 것으로 가정한 가짜 샘플 파일명을 만들고, 부서별 제출 현황표를 만듭니다.

제출물:

- 부서별 제출 현황표
- 파일명 오류 의심 목록
- 누락 부서 후보

예시 파일명:

```text

총무과_행사계획서_수정본.hwpx
민원지적과_행사계획서.pdf
교육청소년과_행사계획서_진짜최종.hwp
```

# 03. 문서 정리하기: 교육대상자 명단 직제순 정렬

## 이 장에서 만들 결과물

이 장에서는 교육대상자 명단을 부서 직제순으로 정리합니다.

최종 결과물은 다음입니다.

- `교육대상자_샘플.csv`: 실습용 가짜 명단
- `직제순_기준표.csv`: 부서 순서를 정한 기준표
- `교육대상자_직제순정리.csv`: 직제순으로 정렬된 명단
- `정리기준_확인메모.md`: 어떤 기준으로 정리했는지 남긴 메모

이 장의 핵심은 단순 정렬이 아닙니다.

> AI가 직제순을 알아서 맞히게 하는 것이 아니라,  
> 기준표를 같이 확인하고  
> 그 기준대로 문서를 정리하게 하는 것입니다.

실제 교육대상자 명단에는 이름, 부서, 직급, 연락처 같은 개인정보 또는 내부정보가 들어갈 수 있습니다. 이 실습에서는 반드시 가짜 데이터나 비식별 샘플만 사용합니다.

## 왜 명단 정리부터 하나요

직원들이 바로 체감하는 AI 활용은 거창한 자동화보다 이런 일입니다.

- 교육대상자 명단을 부서순으로 정리하기
- 참석자 명단에서 중복 제거하기
- 신청자 목록을 소속별로 묶기
- 제출자료 목록을 부서별로 정리하기
- 회의 참석자를 직제순으로 배치하기

이런 일은 단순해 보이지만, 실제로는 기준이 필요합니다.

예를 들어 "직제순으로 정리해줘"라고만 하면 Codex가 임의로 부서 순서를 추측할 수 있습니다. 그런데 직제순은 기관마다 다르고, 같은 기관 안에서도 기준일에 따라 바뀔 수 있습니다.

그래서 먼저 이렇게 물어보는 것이 좋습니다.

```text
교육대상자 명단을 직제순으로 정리하고 싶은데,
네가 정확히 정리하려면 내가 어떤 기준표를 줘야 해?
부서명만 있으면 되는지, 팀명이나 직급도 필요한지 먼저 물어봐줘.
```

이 질문이 중요합니다. AI에게 일을 맡긴다는 것은 정답을 맞히게 하는 것이 아니라, 필요한 기준을 먼저 드러내게 하는 일입니다.

## 준비물 만들기

먼저 실습 폴더를 만듭니다.

```text
codex-public-practice
└─ 03_문서정리_명단_직제순
   ├─ 00_input
   ├─ 01_working
   └─ 02_output
```

`00_input` 폴더에 `교육대상자_샘플.csv`를 만들고 아래 내용을 넣습니다.

```csv
연번,성명,부서,팀,직급,참석구분,비고
1,김가람,교육청소년과,청소년팀,주무관,참석,
2,이도윤,총무과,인사팀,주무관,참석,
3,박하늘,기획예산실,예산팀,팀장,참석,
4,최서연,회계과,계약팀,주무관,불참,출장
5,정지후,홍보소통실,홍보팀,주무관,참석,
6,한유진,교육청소년과,교육지원팀,팀장,참석,
7,오민재,민원지적과,민원팀,주무관,참석,
8,문서윤,총무과,총무팀,팀장,참석,
9,강지안,기획예산실,기획팀,주무관,참석,
10,서하준,회계과,경리팀,팀장,참석,
```

이어서 `00_input/직제순_기준표.csv`를 만듭니다.

```csv
부서순번,부서
1,기획예산실
2,홍보소통실
3,총무과
4,교육청소년과
5,민원지적과
6,회계과
```

이 기준표도 가짜 예시입니다. 실제 기관의 직제순을 쓸 때는 기준일과 출처를 확인해야 합니다.

## 1단계: Codex에게 필요한 기준을 먼저 물어보기

바로 "정렬해줘"라고 하지 않습니다. 먼저 Codex가 어떤 기준을 필요로 하는지 말하게 합니다.

```text
교육대상자 명단을 직제순으로 정리하려고 해.
내가 정확히 정리하려면 어떤 기준을 줘야 해?

현재 가진 파일은 두 개야.
- `00_input/교육대상자_샘플.csv`
- `00_input/직제순_기준표.csv`

바로 정렬하지 말고,
먼저 정리 기준을 확인하기 위한 질문을 해줘.
```

Codex가 물어볼 수 있는 질문은 보통 이렇습니다.

| 질문 | 이유 |
| --- | --- |
| 부서 순서는 어떤 기준표를 따르나요? | 직제순은 기관마다 다르기 때문 |
| 같은 부서 안에서는 팀순으로 정렬하나요? | 부서 안 정렬 기준 필요 |
| 같은 팀 안에서는 직급순인가요, 이름순인가요? | 세부 정렬 기준 필요 |
| 불참자는 포함하나요? | 참석자 명단인지 전체 대상자 명단인지 구분 |
| 연번은 새로 매기나요? | 기존 연번 유지 여부 확인 |

이 질문에 사용자가 답하면서 기준이 만들어집니다.

## 2단계: 정리 기준 확정하기

이 실습에서는 기준을 이렇게 정합니다.

```text
기준은 이렇게 하자.

1. 부서 순서는 `직제순_기준표.csv`를 따른다.
2. 같은 부서 안에서는 팀명을 가나다순으로 정렬한다.
3. 같은 팀 안에서는 직급 순서보다 이름 가나다순을 우선한다.
4. 참석구분이 불참이어도 명단에는 포함한다.
5. 연번은 정렬 후 새로 1번부터 다시 매긴다.
6. 기준표에 없는 부서가 있으면 맨 아래에 두고 `확인필요`로 표시한다.

이 기준으로 작업계획을 먼저 써줘.
```

여기서도 바로 결과물을 만들지 않습니다. 작업계획을 먼저 봅니다.

작업계획에는 최소한 다음이 있어야 합니다.

- 입력 파일
- 사용할 정렬 기준
- 기준표에 없는 부서 처리 방식
- 새 연번 부여 방식
- 최종 결과 파일명
- 검수할 항목

## 3단계: 직제순으로 정리하기

작업계획이 괜찮으면 정리를 맡깁니다.

```text
좋아. 방금 정한 기준대로 명단을 정리해줘.

결과물:
- `02_output/교육대상자_직제순정리.csv`
- `02_output/정리기준_확인메모.md`

주의:
- 원본 `교육대상자_샘플.csv`는 수정하지 마.
- 정렬 후 연번은 새로 매겨줘.
- 기준표에 없는 부서가 있으면 삭제하지 말고 맨 아래에 두고 확인필요로 표시해줘.
```

결과 CSV는 이런 형태가 되어야 합니다.

```csv
연번,성명,부서,팀,직급,참석구분,비고,정리메모
1,강지안,기획예산실,기획팀,주무관,참석,,
2,박하늘,기획예산실,예산팀,팀장,참석,,
3,정지후,홍보소통실,홍보팀,주무관,참석,,
...
```

## 4단계: 결과 검수하기

명단 정리는 결과가 그럴듯해 보여도 반드시 검수해야 합니다.

```text
`02_output/교육대상자_직제순정리.csv`를 검수해줘.

검수할 것:
1. 부서 순서가 `직제순_기준표.csv`와 맞는가
2. 원본 명단의 사람이 빠지지 않았는가
3. 원본에 없던 사람이 추가되지 않았는가
4. 참석/불참 정보가 유지됐는가
5. 연번이 새로 1번부터 매겨졌는가
6. 기준표에 없는 부서가 있다면 확인필요로 표시됐는가

검수 결과를 `02_output/정리기준_확인메모.md`에 추가해줘.
```

이 검수는 중요합니다. 명단 정리에서 가장 흔한 문제는 정렬보다 누락입니다. 사람 한 명이 빠지거나 중복되면 결과가 틀린 것입니다.

## 5단계: 보기 좋은 표로 바꾸기

CSV만 있으면 업무용으로 조금 딱딱합니다. 필요하면 Markdown 표로도 만들 수 있습니다.

```text
정렬된 CSV를 바탕으로
부서별로 보기 좋은 Markdown 표를 만들어줘.

파일명:
- `02_output/교육대상자_직제순정리.md`

구성:
- 부서별 소제목
- 부서별 인원 수
- 성명, 팀, 직급, 참석구분, 비고 표
- 마지막에 전체 참석/불참 인원 요약
```

부서별로 묶으면 사람이 확인하기 쉬워집니다.

## 막혔을 때

### 직제순 기준표가 없을 때

```text
직제순 기준표가 아직 없어.
명단에 나온 부서 목록만 먼저 뽑아주고,
내가 순서를 직접 정할 수 있는 기준표 초안을 만들어줘.
```

### 부서명이 조금씩 다를 때

```text
부서명이 기준표와 조금 다르게 적힌 것 같아.
예를 들어 `교육청소년과`와 `교육 청소년과`처럼 표기가 다른 항목을 찾아서
정규화 후보표를 만들어줘.
바로 고치지는 말고 내가 확인하게 해줘.
```

### 사람이 빠졌는지 걱정될 때

```text
정렬 전후 인원 수를 비교해줘.
성명+부서 기준으로 누락, 중복, 추가된 사람이 있는지 확인해줘.
```

### 실제 명단을 써야 할 때

```text
이 명단에 개인정보나 내부정보가 포함될 수 있어.
Codex에 넣기 전에 어떤 항목을 삭제하거나 가명처리해야 하는지 알려줘.
```

실제 명단을 사용할 때는 기관 보안정책과 개인정보 처리 기준을 먼저 확인해야 합니다.

## 혼자 해보는 과제

아래와 같은 정리 작업으로 바꿔서 실습해 봅니다.

- 부서별 교육 신청자 명단 정리
- 회의 참석자 명단 직제순 정렬
- 제출자료 목록을 부서순으로 정리
- 행사 역할분담표를 부서별로 묶기
- 교육 이수자 명단에서 중복 제거 후 부서순 정렬

대화 시작문은 이렇게 하면 됩니다.

```text
이 명단을 보기 좋게 정리하고 싶은데,
정확히 정리하려면 내가 어떤 기준표를 줘야 해?
부서순, 팀순, 이름순 중 어떤 기준을 먼저 정해야 하는지 질문해줘.
```

## 오늘 배운 절차

1. 명단 파일과 직제순 기준표를 준비한다.
2. Codex에게 먼저 필요한 기준을 물어본다.
3. 부서순, 팀순, 이름순, 참석/불참 처리 기준을 정한다.
4. 원본을 수정하지 않고 정렬 결과 파일을 만든다.
5. 정렬 전후 인원 수와 누락 여부를 검수한다.
6. 필요하면 부서별 Markdown 표로 바꾼다.


# 04. Browser Use: 웹브라우저 조사와 자동화

## 이 장에서 만들 결과물

이 장에서는 Codex에게 브라우저를 직접 쓰게 해 봅니다. 공개 웹사이트를 조사하고, 근거 링크와 확인 결과를 표로 정리합니다. 가능하면 반복 검색도 자동화합니다.

최종 결과물은 다음과 같습니다.

- `조사계획.md`: 무엇을 어디서 확인할지 정리한 계획
- `근거링크표.md`: 제목, 기관, 링크, 확인일, 판단 사유가 들어간 표
- `results.csv`: 반복 검색 결과를 모은 CSV
- `검수메모.md`: 링크가 실제로 열리는지 확인한 기록

이 장에서는 Browser Use를 중심으로 익힙니다. Playwright는 같은 일을 여러 번 반복해야 할 때 쓰는 자동화 방식으로 뒤에 붙입니다.

> 한두 번 보고 판단할 일은 브라우저 조작으로 충분합니다.  
> 같은 검색을 여러 번 반복할 일은 자동화로 넘깁니다.

서버 설정이나 API 설정도 같은 맥락에 있습니다. 개발자센터 화면을 보고, 공식 문서를 확인하고, 오류 메시지를 해석하는 일은 Browser Use/Playwright와 잘 맞습니다. 다만 입문 단계에서 바로 실습하기에는 계정, 권한, 토큰, 환경변수 같은 요소가 많습니다. 그래서 이 장에서는 맛보기 사례로만 보고, Meta 개발자센터에서 Instagram·Threads 분석 API를 준비하는 실습은 10장에서 별도 심화 챕터로 다룹니다.

## Browser Use가 왜 인상적인가요

Browser Use가 재미있는 이유는 AI가 대화창 안에서만 말하는 것이 아니라, 실제 웹 화면을 열고, 클릭하고, 읽고, 다음 행동을 제안하기 때문입니다.

이때도 완성된 프롬프트를 한 번에 넣어야 하는 것은 아닙니다. 실제로는 이렇게 대화를 시작하는 편이 자연스럽습니다.

```text
이 사이트에서 내가 뭘 눌러야 할지 잘 모르겠어.
먼저 화면을 보고 가능한 경로를 설명해줘.
최종 취소나 결제 버튼은 내가 직접 누를게.
```

Browser Use의 장점은 화면을 보면서 조건을 계속 보완할 수 있다는 점입니다. "여기가 아닌 것 같다", "이 버튼은 위험해 보인다", "이 문구가 무슨 뜻이냐"처럼 대화하면서 진행합니다.

예를 들어 이런 일을 맡길 수 있습니다.

| 유형 | 예시 | AI가 해줄 수 있는 일 | 사람이 직접 해야 하는 일 |
| --- | --- | --- | --- |
| 개인비서형 | 볼로테아 같은 항공사 예약 취소 방법 확인 | 예약 취소 메뉴 찾기, 약관 확인, 취소 수수료와 환불 조건 정리 | 로그인, 본인 확인, 최종 취소 버튼 클릭 |
| 결제 확인형 | 잘못 결제된 멤버십 취소 방법 찾기 | 고객센터 경로, 해지 메뉴, 환불 가능 조건 정리 | 계정 인증, 결제 취소 최종 승인 |
| 여행 확인형 | 호텔 예약 중 조식 포함 여부 확인 | 예약 메일이나 공개 예약정보 기준으로 확인할 항목 정리 | 개인 예약번호 입력, 개인정보 확인 |
| 업무 조사형 | 공공기관 AI 교육 사례 찾기 | 공개 사이트 검색, 근거 링크표 작성, 후보 제외 사유 정리 | 최종 인용 여부 판단 |
| 서버 세팅형 | 도메인, DNS, 배포 콘솔 설정 보조 | 설정 화면에서 필요한 항목 찾기, 입력값 체크리스트 작성, 오류 메시지 해석 | 비밀번호 입력, API 키 발급, 결제 또는 삭제 버튼 클릭 |

이런 사례가 교육에서 강력한 이유는 직원들이 바로 이해하기 때문입니다.

> "아, AI가 검색 답변만 하는 게 아니라  
> 내가 웹에서 헤매던 일을 같이 보고 처리할 수 있구나."

다만 중요한 원칙이 있습니다. 취소, 결제, 삭제, 배포, 권한 변경처럼 되돌리기 어려운 행동은 AI가 알아서 누르게 하지 않습니다. AI는 찾고, 비교하고, 설명하고, 체크리스트를 만들게 합니다. 마지막 결정과 클릭은 사람이 합니다.

## 안전 원칙

직원 교육 실습은 공개 웹사이트만 사용합니다.

사용하면 안 되는 화면은 다음입니다.

- 내부 행정시스템
- 로그인한 업무 시스템
- 개인정보가 보이는 민원, 인사, 계약, 계좌 화면
- 기관 내부 검토자료
- 비공개 게시판
- 결제, 예약 취소, 계정 삭제, 서버 삭제처럼 되돌리기 어려운 최종 실행 화면

사용해도 되는 예시는 다음입니다.

- 법제처 국가법령정보센터
- 중앙선거관리위원회 공개 자료
- 지자체 공개 고시공고
- 공모전 공개 사이트
- 공개 보도자료
- 공개 여행정보 사이트

개인 계정이나 서버 콘솔을 다루는 시연은 강사가 별도로 준비한 샘플 계정이나 테스트 환경에서만 보여줍니다. 직원 실습 과제로는 공개 웹자료 조사부터 시작합니다.

## 예제 A: 개인비서형 Browser Use 맛보기

이 예제는 실제 실습보다는 시연용입니다. 계정, 예약번호, 결제정보가 들어가기 때문입니다.

```text
볼로테아 항공권 예약을 취소해야 하는 상황이라고 가정해보겠습니다.
실제 예약정보는 입력하지 않고,
먼저 공개 웹에서 취소 절차와 주의사항만 조사해주세요.

확인할 것:
- 예약 취소 메뉴가 어디에 있는지
- 로그인이나 예약번호가 필요한지
- 취소 수수료 또는 환불 조건을 어디서 확인하는지
- 최종 취소 전에 사람이 확인해야 할 항목

주의:
- 실제 예약번호, 여권번호, 결제정보는 입력하지 않습니다.
- 최종 취소 버튼은 절대 누르지 않습니다.
- 결과는 "사용자가 직접 확인할 체크리스트"로 정리해주세요.
```

이 요청의 핵심은 AI에게 취소를 시키는 것이 아닙니다. 취소 화면까지 가는 길을 찾아주고, 내가 누르기 전에 확인할 조건을 정리하게 하는 것입니다.

같은 방식으로 아래 작업도 시연할 수 있습니다.

```text
잘못 결제된 멤버십을 취소하려고 합니다.
공개 도움말과 계정 설정 메뉴 기준으로
해지 경로, 환불 가능성 확인 위치, 고객센터 문의 전 준비할 정보를 정리해주세요.
최종 해지나 결제 취소 버튼은 제가 직접 누릅니다.
```

```text
호텔 예약 중 어떤 예약이 조식 포함인지 기억이 나지 않습니다.
예약 확인 메일이나 예약 사이트에서 확인해야 할 항목을 체크리스트로 만들어주세요.
개인정보가 필요한 화면은 제가 직접 확인하겠습니다.
```

## 예제 B: 서버 세팅 보조

Browser Use는 웹서비스 설정에도 유용합니다. 예를 들어 도메인 연결, 배포 콘솔, DNS 설정처럼 화면이 복잡한 작업에서 도움을 받을 수 있습니다.

직원 교육에서는 실제 서버를 바꾸지 않고, 테스트 프로젝트나 공개 문서를 기준으로 설명합니다.

```text
웹앱 배포 후 도메인을 연결해야 합니다.
브라우저에서 설정 화면을 보면서 필요한 작업을 체크리스트로 정리해주세요.

확인할 것:
- 도메인 연결 메뉴 위치
- DNS에 추가해야 할 레코드 종류
- 입력해야 할 값
- 설정 후 반영 확인 방법
- 실패했을 때 확인할 오류 메시지

주의:
- 실제 API 키, 비밀번호, 결제정보는 입력하지 않습니다.
- 삭제, 권한 변경, 결제 같은 최종 버튼은 누르지 않습니다.
- 제가 최종 확인할 수 있게 단계별 체크리스트로 정리해주세요.
```

서버 세팅에서 AI가 잘하는 일은 "어디를 봐야 하는지"와 "오류 메시지가 무슨 뜻인지"를 설명하는 것입니다. 사람이 해야 하는 일은 권한, 결제, 삭제, 배포 승인처럼 책임이 따르는 최종 판단입니다.

API 설정도 여기에 포함됩니다. 예를 들어 Meta 개발자센터에서 Instagram이나 Threads 분석 API를 설정할 때도 Codex는 공식 문서 확인, 필요한 권한 정리, `.env.example` 작성, 테스트 호출 오류 해석을 도울 수 있습니다. 하지만 이 작업은 토큰과 앱 권한을 다루므로 이 장에서 바로 따라 하지는 않습니다. 10장에서 별도 심화 실습으로 진행합니다.

## 예제 C: 공개자료 조사 실습

이 장에서는 다음 예제를 사용합니다.

```text
주제: 청소년 대상 AI 교육 프로그램을 기획할 때 참고할 공개 사례 찾기
확인할 자료:
- 지자체 또는 공공기관의 AI 교육 사례
- 모집 대상
- 교육 내용
- 운영 방식
- 근거 링크
```

주제는 행정업무와 연결되지만, 실습에서는 공개 웹자료만 봅니다.

## 1단계: 조사 질문을 좁히기

웹 조사를 맡길 때 가장 흔한 실수는 이렇게 말하는 것입니다.

```text
AI 교육 사례 찾아줘.
```

이렇게 요청하면 결과가 넓고 흐릿해집니다. 먼저 조사 질문을 좁혀야 합니다.

아래 문장은 대화 시작 예시입니다. 짧게 시작하고 싶다면 "이 주제를 조사하려면 어떤 질문부터 정해야 해?"라고 물어봐도 됩니다.

```text
청소년 대상 AI 교육 프로그램을 기획하기 위해 공개 웹자료를 조사하려고 합니다.

먼저 바로 검색하지 말고 조사계획을 세워주세요.

조사계획에는 다음을 포함해주세요.
- 검색할 핵심 질문 5개
- 우선 확인할 공개 사이트 유형
- 검색어 후보
- 제외할 자료 기준
- 최종 결과표 컬럼

주의:
- 내부 시스템이나 비공개 자료는 사용하지 않습니다.
- 공개 웹자료만 조사합니다.
- 최신성과 출처가 불분명한 블로그 글은 보조자료로만 취급합니다.

결과는 `01_working/조사계획.md`로 작성해주세요.
```

기대하는 조사 질문은 이런 식입니다.

| 질문 | 이유 |
| --- | --- |
| 청소년 대상 AI 교육은 어떤 기관이 운영했는가 | 벤치마킹 대상 확인 |
| 교육 대상은 초등/중등/고등 중 어디인가 | 대상별 난이도 차이 확인 |
| 생성형 AI 실습이 포함됐는가 | Codex 교육과 연결 여부 |
| 운영 방식은 캠프, 특강, 정규과정 중 무엇인가 | 우리 기관 적용 가능성 확인 |
| 결과물이나 발표회가 있었는가 | 최종 프로젝트 설계 참고 |

## 2단계: 브라우저 조사를 맡기기

조사계획이 나오면 공개 웹 조사를 맡깁니다.

```text
`01_working/조사계획.md`를 기준으로 공개 웹자료를 조사해주세요.

조사 대상:
- 지자체 또는 공공기관의 청소년 AI 교육 사례
- 교육청, 도서관, 청소년센터, 평생학습기관의 공개 프로그램
- 보도자료나 모집공고처럼 출처가 확인되는 자료

결과 작성 방식:
- 바로 결론을 쓰지 말고, 먼저 후보 자료를 표로 정리해주세요.
- 각 행에는 제목, 기관명, 게시일 또는 확인일, 링크, 핵심 내용, 활용 가능성, 제외 여부를 포함해주세요.
- 링크가 불분명한 자료는 제외 후보로 표시해주세요.
- 결과는 `02_output/근거링크표.md`로 저장해주세요.
```

Codex가 브라우저를 직접 사용할 수 있는 환경이면 검색, 클릭, 확인을 맡길 수 있습니다. 브라우저 도구가 없는 환경이면 Codex가 검색어와 조사표 양식을 제안하고, 사람이 링크를 열어 확인한 뒤 다시 붙여 넣는 방식으로 진행합니다.

중요한 것은 "검색 결과를 믿는 것"이 아니라 "근거 링크를 남기는 것"입니다.

## 3단계: 근거링크표 형식 맞추기

근거링크표는 최소한 아래 컬럼을 가져야 합니다.

```text
번호 / 자료명 / 기관명 / 게시일 / 확인일 / 링크 / 핵심 내용 / 우리 실습에 쓸 수 있는 점 / 주의할 점 / 채택 여부
```

Codex에게 표 형식을 다시 정리하게 합니다.

```text
`02_output/근거링크표.md`를 아래 컬럼 순서로 다시 정리해주세요.

번호 / 자료명 / 기관명 / 게시일 / 확인일 / 링크 / 핵심 내용 / 우리 실습에 쓸 수 있는 점 / 주의할 점 / 채택 여부

정리 기준:
- 같은 기관 자료가 중복되면 가장 직접적인 자료만 남겨주세요.
- 링크가 없는 자료는 채택하지 말고 제외 사유를 적어주세요.
- 블로그나 카페 글은 공식 자료가 아닐 경우 보조자료로 표시해주세요.
```

## 4단계: 반복 검색이 필요한지 판단하기

한두 개만 찾으면 되는 일은 여기서 끝내도 됩니다. 하지만 검색어가 여러 개라면 반복 작업으로 바꿀 수 있습니다.

예를 들어 검색어가 이렇게 많다고 해보겠습니다.

```text
청소년 AI 교육 지자체
청소년 생성형 AI 교육 공공기관
도서관 AI 교육 청소년
청소년센터 인공지능 교육
AI 캠프 청소년 지자체
```

이런 경우에는 검색어 목록을 파일로 만들고 반복 검색 결과를 모을 수 있습니다.

`00_input/search_terms.csv` 파일을 만들고 아래 내용을 넣습니다.

```csv
keyword
청소년 AI 교육 지자체
청소년 생성형 AI 교육 공공기관
도서관 AI 교육 청소년
청소년센터 인공지능 교육
AI 캠프 청소년 지자체
```

그다음 Codex에게 반복 검색 방식도 같이 설계하게 합니다.

```text
`00_input/search_terms.csv`의 검색어를 기준으로 공개 웹 검색 결과를 수집하는 방식을 제안해주세요.

가능하다면 Playwright 같은 브라우저 자동화 도구를 사용해
각 검색어별 상위 결과 제목, 링크, 출처를 `02_output/results.csv`로 저장해주세요.

단, 자동화가 현재 환경에서 어렵다면
사람이 수동으로 검색할 수 있는 체크리스트와 입력용 표를 대신 만들어주세요.

주의:
- 로그인 필요한 사이트는 제외합니다.
- 내부 시스템은 사용하지 않습니다.
- 수집한 링크는 반드시 사람이 한 번 열어 검수해야 합니다.
```

## 5단계: 자동화 결과 검수하기

자동으로 모은 결과는 반드시 검수해야 합니다. 검색 결과 CSV는 "후보 목록"이지 "정답 목록"이 아닙니다.

검수도 사용자가 기준을 다 알고 있어야 하는 것이 아닙니다. 먼저 "이 결과를 믿기 전에 무엇을 확인해야 하냐"고 물어본 뒤, 아래 항목을 보태면 됩니다.

```text
`02_output/results.csv`를 검수해주세요.

검수 기준:
1. 링크가 실제로 열리는가
2. 자료 출처가 공식기관 또는 신뢰 가능한 공개자료인가
3. 제목만 보고 관련 있어 보이지만 실제 내용은 다른 자료가 있는가
4. 중복 자료가 있는가
5. 우리 교육자료에 인용하거나 참고하기 부적절한 자료가 있는가

검수 결과는 `02_output/검수메모.md`에 표로 정리해주세요.
```

## 막혔을 때

### 브라우저 조작이 안 될 때

Codex에게 이렇게 말합니다.

```text
현재 환경에서 브라우저 조작이 어렵다면,
내가 직접 검색해서 붙여 넣을 수 있도록 검색어 목록과 입력용 표를 만들어주세요.
```

### 결과가 너무 많을 때

```text
자료가 너무 많습니다.
공식기관 자료를 우선하고, 블로그/카페/광고성 자료는 제외해주세요.
최종 후보는 10개 이하로 줄이고 제외 사유를 남겨주세요.
```

### 링크만 있고 판단이 없을 때

```text
링크 목록만으로는 부족합니다.
각 자료가 왜 유용한지, 우리 교육에 어떻게 참고할 수 있는지 판단 사유를 추가해주세요.
```

## 혼자 해보는 과제

아래 주제 중 하나를 골라 같은 방식으로 조사합니다.

- 보조금 정산 교육자료 공개 사례
- 공공기관 생성형 AI 활용 가이드
- 지자체 청년정책 공모사업 사례
- 디지털 문해교육 프로그램 사례
- 민원응대 매뉴얼 공개자료

## 오늘 배운 절차

1. 바로 검색하지 않고 조사계획을 만든다.
2. 공개 웹자료만 사용한다.
3. 링크, 기관명, 확인일, 판단 사유를 남긴다.
4. 반복 검색이 필요하면 검색어 목록을 만든다.
5. 자동화 결과는 후보로 보고 다시 검수한다.

# 05. HTML 보고서 만들기

## 이 장에서 만들 결과물

이 장에서는 앞 장에서 만든 조사 결과를 HTML 보고서로 바꿉니다.

최종 결과물은 다음입니다.

- `AI교육_공개사례_보고서.html`
- `AI교육_공개사례_보고서_검수.md`

HTML 보고서는 웹사이트를 배포하자는 뜻이 아닙니다. 브라우저에서 열어 보기 좋은 업무 공유물입니다.

> HTML 보고서는  
> 표, 요약, 근거 링크, 캡처, 확인일을  
> 한 화면에서 읽기 좋게 묶는 방법입니다.

이 장에서도 "HTML을 이렇게 만들어라"라는 완성형 지시보다, 먼저 Codex에게 보고서 구조를 묻는 방식이 좋습니다.

```text
이 조사 결과를 사람들이 보기 쉽게 공유하려고 해.
HTML 보고서로 만들려면 어떤 구성부터 정해야 해?
읽는 사람이 제일 먼저 봐야 할 정보가 뭐야?
```

Codex가 목차와 화면 구성을 제안하면, 그중 필요한 것만 남기고 실제 HTML 생성을 맡깁니다.

## 왜 Markdown이 아니라 HTML인가요

Markdown은 쓰기 쉽습니다. 하지만 누군가에게 보여줄 때는 HTML이 더 편한 경우가 있습니다.

HTML 보고서의 장점은 다음입니다.

- 브라우저에서 바로 열린다.
- 표와 색상을 보기 좋게 정리할 수 있다.
- 링크를 클릭할 수 있다.
- 캡처 이미지를 함께 넣을 수 있다.
- PDF로 인쇄하거나 공유하기 쉽다.

이 장에서는 디자인을 화려하게 만드는 것이 목표가 아닙니다. 읽기 좋고 검수하기 쉬운 보고서를 만드는 것이 목표입니다.

## 준비물

앞 장에서 만든 파일 중 하나를 사용합니다.

- `02_output/근거링크표.md`
- `02_output/results.csv`
- `02_output/검수메모.md`

파일이 없다면 아래 샘플을 `00_input/근거링크표_샘플.md`로 만듭니다.

```markdown
| 번호 | 자료명 | 기관명 | 확인일 | 링크 | 핵심 내용 | 활용 가능성 | 채택 여부 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 청소년 AI 캠프 운영 사례 | 샘플시청 | 2026-05-22 | https://example.com/ai-camp | 청소년 대상 AI 체험 교육 운영 | 실습형 교육 구성 참고 | 채택 |
| 2 | 도서관 디지털 교육 안내 | 샘플도서관 | 2026-05-22 | https://example.com/library-ai | 도서관에서 기초 디지털 교육 운영 | 초급자 설명 방식 참고 | 보조 |
| 3 | 생성형 AI 활용 가이드 | 샘플기관 | 2026-05-22 | https://example.com/ai-guide | 생성형 AI 사용 시 주의사항 안내 | 안전수칙 작성 참고 | 채택 |
```

## 1단계: 보고서 구조를 먼저 정하기

바로 HTML을 만들게 하지 말고, 보고서 구조부터 대화로 잡습니다.

```text
`00_input/근거링크표_샘플.md`를 바탕으로
브라우저에서 열 수 있는 HTML 보고서를 만들려고 합니다.

먼저 HTML을 만들지 말고 보고서 목차와 화면 구성을 제안해주세요.

보고서에는 다음이 들어가야 합니다.
- 제목
- 작성 목적
- 한눈에 보는 요약
- 채택 자료 표
- 보조자료 표
- 제외하거나 주의할 자료
- 다음 조치
- 확인일

직원들이 읽기 쉽게 너무 화려하지 않은 업무용 스타일로 구성해주세요.
```

좋은 목차는 보통 이렇게 나옵니다.

1. 보고서 제목
2. 요약
3. 핵심 판단
4. 근거 자료 목록
5. 활용 가능한 요소
6. 주의할 점
7. 다음 조치

## 2단계: HTML 파일 만들기

구조가 괜찮으면 HTML 생성을 요청합니다.

```text
제안한 구조대로 `02_output/AI교육_공개사례_보고서.html`을 만들어주세요.

디자인 기준:
- 브라우저에서 바로 열 수 있는 단일 HTML 파일로 만들어주세요.
- 외부 CSS 파일 없이 HTML 안에 스타일을 포함해주세요.
- 글자는 너무 작지 않게 해주세요.
- 표는 가로로 넘치지 않게 해주세요.
- 링크는 클릭할 수 있게 해주세요.
- 공공기관 업무 보고서처럼 차분하고 읽기 쉽게 만들어주세요.

내용 기준:
- 원본 근거표에 없는 사실을 새로 만들지 마세요.
- 확인일을 보고서 상단 또는 하단에 표시해주세요.
- 채택 자료와 보조자료를 구분해주세요.
```

## 3단계: 브라우저에서 열어 보기

HTML 파일이 만들어지면 파일 탐색기에서 `02_output` 폴더를 열고, `AI교육_공개사례_보고서.html`을 더블클릭합니다.

확인할 것은 다음입니다.

- 브라우저에서 열리는가
- 제목과 요약이 바로 보이는가
- 표가 화면 밖으로 심하게 넘치지 않는가
- 링크가 클릭되는가
- 한글이 깨지지 않는가
- 내용이 너무 빽빽하지 않은가

만약 한글이 깨지면 Codex에게 이렇게 말합니다.

```text
HTML 파일을 열었을 때 한글이 깨질 수 있으니
`<meta charset="UTF-8">`가 들어가 있는지 확인하고,
없으면 추가해서 수정해주세요.
```

## 4단계: 보기 좋게 다듬기

처음 HTML은 대체로 투박합니다. 한 번 더 다듬게 합니다.

```text
HTML 보고서를 업무 공유용으로 조금 더 읽기 좋게 다듬어주세요.

수정 기준:
- 제목 아래에 3줄 이내의 핵심 요약을 넣어주세요.
- 채택 자료는 눈에 잘 띄게 표시해주세요.
- 표의 긴 문장은 줄바꿈이 되게 해주세요.
- 모바일 폭에서도 글자가 겹치지 않게 해주세요.
- 장식은 줄이고, 정보가 잘 보이게 해주세요.
```

여기서 중요한 것은 "예쁜 페이지"가 아닙니다. 보고서를 보는 사람이 빠르게 판단할 수 있어야 합니다.

## 5단계: 검수 파일 만들기

HTML을 만든 뒤에는 검수 기록을 남깁니다.

```text
`02_output/AI교육_공개사례_보고서.html`을 기준으로
`02_output/AI교육_공개사례_보고서_검수.md`를 만들어주세요.

검수 항목:
1. HTML 파일이 브라우저에서 열리는가
2. 제목, 요약, 근거표, 다음 조치가 있는가
3. 링크가 클릭 가능한 형태인가
4. 원본에 없는 사실이 추가되지 않았는가
5. 확인일이 표시되어 있는가
6. 표가 너무 넓어 읽기 어렵지 않은가
7. 내부자료나 개인정보가 포함되어 있지 않은가

각 항목은 통과/확인필요/수정완료 중 하나로 표시해주세요.
```

# 06. 공개 Skill URL로 사용해보기

## 이 장에서 만들 결과물

이 장에서는 skills.sh나 GitHub에서 마음에 드는 Skill을 찾고, 그 URL을 Codex에게 던져서 써봅니다.

최종 결과물은 다음입니다.

- `skill_사용메모.md`: 어떤 Skill URL을 써봤는지 적은 메모
- `youtube_downloader_실습기록.md`: YouTube downloader Skill을 써본 기록
- 다운로드 결과 파일 또는 실행 결과 확인 메모

이 장은 어렵게 생각할 필요가 없습니다.

> Skill을 써보는 첫 방법은 간단합니다.  
> skills.sh나 GitHub에서 좋아 보이는 Skill을 찾고,  
> URL을 복사해서 Codex에게 "이거 써볼래?"라고 물어보면 됩니다.

## Skill을 찾는 곳

처음에는 두 곳만 보면 됩니다.

| 위치 | 무엇을 하는 곳인가 |
| --- | --- |
| https://www.skills.sh/ | 공개 Skill을 검색하는 곳 |
| https://github.com/ | Skill 원본이 올라와 있는 곳 |

GitHub가 낯설어도 괜찮습니다. 사용자가 코드를 읽을 필요는 없습니다. 링크를 Codex에게 주고 "이게 뭔지 설명해줘"라고 하면 됩니다.

## 가장 쉬운 흐름

복잡하게 설치 방법부터 외우지 않습니다. 흐름은 이것뿐입니다.

1. skills.sh에 들어간다.
2. 검색어를 넣는다.
3. 마음에 드는 Skill 페이지를 연다.
4. 주소창의 URL을 복사한다.
5. Codex에게 붙여넣고 말한다.

```text
이 Skill 좋아 보이는데, 너 이거 써볼래?
링크를 보고 어떤 일을 하는 Skill인지 먼저 설명해줘.

[여기에 Skill URL 붙여넣기]
```

GitHub도 똑같습니다.

```text
이 GitHub 저장소에 있는 Skill을 써보고 싶어.
뭘 하는 Skill인지, 어떻게 쓰면 되는지 쉽게 설명해줘.

[여기에 GitHub URL 붙여넣기]
```

이게 전부입니다. 설치 명령을 사람이 먼저 해석할 필요가 없습니다. Codex가 페이지를 보고, 어떤 Skill인지 설명하고, 지금 PC에서 쓸 수 있는지 확인하고, 필요한 다음 단계를 제안하게 하면 됩니다.

## 예제: YouTube downloader Skill 찾아보기

YouTube downloader는 처음 써보기 좋은 예제입니다. 이유는 단순합니다.

```text
유튜브 링크를 주면 영상 파일이나 오디오 파일로 저장한다.
```

무엇을 하는지 바로 이해됩니다.

### 1단계: skills.sh에서 검색하기

브라우저에서 https://www.skills.sh/ 에 들어갑니다.

검색어는 이렇게 넣어봅니다.

```text
youtube
youtube downloader
yt-dlp
video downloader
```

예를 들어 이런 페이지를 찾을 수 있습니다.

- https://skills.sh/crazynomad/skills/youtube-downloader
- https://skills.sh/jackspace/claudeskillz/youtube-downloader
- https://skills.sh/lwmxiaobei/yt-dlp-skill/yt-dlp

이 중 하나를 고릅니다. 처음에는 첫 번째 링크 하나만 해도 충분합니다.

### 2단계: URL을 Codex에게 던지기

Skill 페이지 URL을 복사해서 Codex에게 말합니다.

```text
이 YouTube downloader Skill 써보고 싶어.
이 링크를 보고 뭘 하는 Skill인지 쉽게 설명해줘.
그리고 내가 이걸 쓰려면 다음에 뭘 하면 되는지 알려줘.

https://skills.sh/crazynomad/skills/youtube-downloader
```

Codex가 할 일은 보통 다음입니다.

- Skill이 무슨 일을 하는지 설명
- 설치가 필요한지 확인
- 설치 명령이 있으면 읽어줌
- 필요한 도구가 있는지 확인
- 테스트할 때 주의할 점 알려줌

사용자는 그 설명을 보고 "좋아, 해보자"라고 이어가면 됩니다.

```text
좋아. 그럼 이 Skill을 지금 PC에서 쓸 수 있는지 확인해줘.
설치가 필요하면 설치 전에 뭐가 설치되는지 먼저 설명해줘.
```

## 설치 명령은 사람이 외우지 않아도 됩니다

skills.sh 페이지에는 `npx skills add ...` 같은 명령이 나올 수 있습니다.

이걸 사람이 이해하려고 애쓸 필요는 없습니다. 그냥 Codex에게 물어봅니다.

```text
페이지에 설치 명령이 있는데, 이게 무슨 뜻이야?
내 PC에 뭘 설치하는 거고, 어디에 들어가는지 설명해줘.
문제 없으면 네가 진행해줘.
```

설치가 막히면 이렇게 말합니다.

```text
설치가 안 되네.
오류 메시지를 보고 왜 안 되는지 쉽게 설명해줘.
설치 없이 이 Skill 설명만 보고 따라할 수 있는 방법이 있으면 알려줘.
```

이 장의 핵심은 명령어가 아닙니다. URL을 주고 Codex가 읽게 하는 것입니다.

## GitHub에서 찾았을 때도 똑같이 하기

GitHub에서 Skill을 발견했다면 저장소 URL을 복사합니다.

```text
이 GitHub 저장소에 있는 Skill을 써보고 싶어.
내가 코드를 읽을 줄 모르니까,
네가 먼저 이 저장소가 뭘 하는지 쉽게 설명해줘.

확인할 것:
- 어떤 Skill이 들어 있는지
- 어떻게 설치하거나 사용할 수 있는지
- 위험해 보이는 작업은 없는지
- 초보자가 테스트해도 괜찮은지

[GitHub URL]
```

여기서도 사람이 먼저 `SKILL.md`를 열고 분석할 필요는 없습니다. Codex가 읽고 설명하게 합니다.

## 그래도 확인해야 할 안전수칙

쉽게 쓰되, 아무거나 막 설치하면 안 됩니다. 아래 정도는 꼭 확인합니다.

```text
설치하기 전에 이것만 확인해줘.
1. 내 파일을 지우거나 바꾸는 동작이 있어?
2. 비밀번호, 계정 토큰, 결제정보를 요구해?
3. 다운로드한 파일을 어디에 저장해?
4. 저작권이나 약관상 조심할 점이 있어?
```

YouTube downloader는 특히 저작권을 조심합니다.

실습에 쓰기 좋은 자료:

- 내가 직접 올린 영상
- 공개 교육자료 중 다운로드가 허용된 영상
- 저작권 문제가 없는 테스트 영상

피해야 할 자료:

- 영화, 방송, 음악 영상
- 유료 강의
- 저작권자가 다운로드를 허용하지 않은 영상
- 내려받은 뒤 다른 사람에게 재배포하려는 영상

## YouTube downloader 실행해보기

Codex가 설치 또는 사용 준비가 됐다고 하면 테스트 URL을 줍니다.

```text
좋아. 이 YouTube URL로 테스트해보자.
영상으로 저장할 수 있는지 먼저 확인하고,
저장 위치와 파일명을 알려준 다음 진행해줘.

URL: [테스트용 YouTube URL]
```

오디오만 필요하면 이렇게 말합니다.

```text
이번에는 영상 말고 오디오만 MP3로 추출하고 싶어.
가능하면 저장 위치와 파일명을 먼저 알려주고 진행해줘.
```

다운로드가 끝나면 확인합니다.

```text
결과 파일이 어디에 생겼는지 알려줘.
파일명, 확장자, 용량, 열어보는 방법을 정리해줘.
```

## 결과 메모 만들기

마지막에는 아주 짧게 메모를 남깁니다.

```text
이번 Skill 사용 기록을 `youtube_downloader_실습기록.md`로 정리해줘.

포함할 것:
- 사용한 Skill URL
- 내가 준 테스트 URL
- 만든 파일
- 저장 위치
- 막힌 점
- 다음에 다시 쓸 때 기억할 점
```

## 막혔을 때

### Skill 페이지가 뭔 말인지 모르겠을 때

```text
이 Skill 페이지가 무슨 말인지 모르겠어.
초보자 기준으로 "이 Skill이 하는 일", "내가 준비할 것", "첫 실행 방법"만 쉽게 설명해줘.
```

### 설치 명령이 무서울 때

```text
이 설치 명령을 실행해도 되는지 모르겠어.
실행하면 내 PC에서 무슨 일이 생기는지 쉬운 말로 설명해줘.
찝찝하면 설치하지 말고 대안도 알려줘.
```

### 실행이 안 될 때

```text
실행이 안 됐어.
오류 메시지를 보고 원인을 쉬운 말로 설명해줘.
내가 해야 할 다음 행동을 3단계 이하로 정리해줘.
```

### 다른 Skill도 찾아보고 싶을 때

```text
skills.sh에서 내가 쓸 만한 Skill을 더 찾아보고 싶어.
업무용으로 바로 이해하기 쉬운 Skill 5개를 검색어와 함께 추천해줘.
```

## 혼자 해보는 과제

skills.sh 또는 GitHub에서 Skill 하나를 골라 URL을 Codex에게 줍니다.

추천 검색어:

```text

pdf
browser
powerpoint

```

Codex에게 이렇게 말합니다.

```text

내가 첫 테스트를 하려면 뭘 준비해야 하는지 알려줘.

[Skill URL]
```

## 오늘 배운 절차

1. skills.sh나 GitHub에서 Skill을 찾는다.
2. URL을 복사한다.
3. Codex에게 "이거 써볼래?"라고 묻는다.
4. Codex가 설명하게 한다.
5. 설치나 실행이 필요하면 Codex가 안내하게 한다.
6. 테스트 후 결과 파일과 주의사항을 메모한다.

# 07. Skill로 남기기

## 이 장에서 만들 결과물

이 장에서는 앞 장에서 성공한 작업을 다음에도 반복할 수 있도록 `SKILL.md` 초안으로 정리합니다.

최종 결과물은 다음입니다.

- `SKILL.md`
- `테스트입력자료_목록.md`
- `검수기준.md`

중요한 점은 이것입니다.

> Skill은 처음부터 만드는 목표가 아닙니다.  
> 내가 한 번 해낸 일을  
> 다음에 덜 헤매려고 남기는 매뉴얼입니다.

Skill 작성도 완성된 프롬프트 하나로 끝나는 일이 아닙니다. 먼저 Codex에게 질문을 만들게 하고, 사용자가 답하면서 정리하는 편이 좋습니다.

```text
이 작업을 다음에도 반복할 수 있게 Skill로 남기고 싶어.
네가 Skill을 만들려면 나에게 무엇을 물어봐야 해?
먼저 질문 목록부터 만들어줘.
```

그 질문에 답하다 보면 발동 조건, 입력자료, 처리 순서, 검수 기준이 자연스럽게 정리됩니다.

## Skill로 남길 만한 일인지 판단하기

모든 일을 Skill로 만들 필요는 없습니다.

Skill로 남기면 좋은 일은 다음과 같습니다.

- 다음 달에도 할 일
- 다른 직원도 따라 할 일
- 입력자료는 매번 바뀌지만 절차는 비슷한 일
- 결과물 형식이 정해져 있는 일
- 검수 기준이 중요한 일
- 매번 설명하기 귀찮은 일

Skill로 만들기 애매한 일은 다음과 같습니다.

- 한 번만 하고 끝나는 일
- 판단 기준이 계속 바뀌는 일
- 입력자료가 비공개라 교육용으로 재현하기 어려운 일
- 아직 한 번도 성공해 보지 못한 일

이 장에서는 앞 장의 `video-to-manual` 실행 경험을 예시로 사용합니다.

## 1단계: 작업 회고부터 쓰기

Skill을 만들기 전에 회고를 씁니다. 회고 없이 바로 `SKILL.md`를 만들면 중요한 시행착오가 빠집니다.

Codex에게 먼저 회고 질문을 만들게 합니다.

```text
앞 장에서 실행한 작업을 Skill로 남기기 전에
작업 회고를 먼저 정리해주세요.

정리할 항목:
- 이 작업의 목적
- 사용한 입력자료
- 최종 결과물
- 중간에 헤맨 지점
- 다시 할 때 미리 정해야 할 기준
- 결과물을 검수할 때 본 항목

결과는 `01_working/작업회고.md`로 저장해주세요.
```

회고에는 실패도 들어가야 합니다. 실패를 빼면 다음에 똑같이 헤맵니다.

예:

```text
- 영상 캡처가 부족하면 단계 설명이 짧아졌다.
- "직원이 글만 보고 따라할 수 있게"라고 명시해야 설명이 자세해졌다.
- 결과물이 PPTX까지 필요한지 Markdown만 필요한지 처음에 정해야 했다.
```

## 2단계: Skill의 발동 조건 정하기

Skill에는 "언제 이 Skill을 써야 하는지"가 필요합니다.

발동 조건도 Codex에게 먼저 후보를 제안하게 합니다.

```text
`01_working/작업회고.md`를 보고
이 작업을 Skill로 만든다면 언제 발동해야 하는지 정리해주세요.

좋은 발동 조건:
- 사용자가 어떤 말을 했을 때 이 Skill을 써야 하는지
- 어떤 입력자료가 있을 때 적합한지
- 반대로 어떤 경우에는 쓰면 안 되는지

결과는 `01_working/발동조건.md`로 저장해주세요.
```

예시는 다음과 같습니다.

```text
이 Skill은 사용자가 "화면녹화로 매뉴얼 만들어줘", "영상 보고 단계별 설명서 만들어줘",
"캡처 없이도 따라할 수 있게 튜토리얼로 정리해줘"라고 요청할 때 사용한다.

단, 영상에 개인정보, 내부 시스템, 비공개 자료가 포함된 경우에는 먼저 사용자에게 확인하고,
교육용으로 공개 가능한 범위만 다룬다.
```

## 3단계: 입력자료와 출력자료 정하기

Skill은 입력과 출력이 분명해야 합니다.

```text
이 Skill의 입력자료와 출력자료를 정리해주세요.

입력자료:
- 필수 입력
- 선택 입력
- 있으면 좋은 자료
- 사용하면 안 되는 자료

출력자료:
- 반드시 만들어야 하는 파일
- 선택적으로 만들 수 있는 파일
- 파일명 규칙

결과는 `01_working/입출력정의.md`로 저장해주세요.
```

예:

| 구분 | 내용 |
| --- | --- |
| 필수 입력 | 화면녹화 영상 파일 |
| 선택 입력 | 원하는 문체, 대상 독자, 결과물 형식 |
| 금지 입력 | 개인정보, 내부 시스템 계정, 비공개 업무자료 |
| 필수 출력 | 단계별 매뉴얼 Markdown |
| 선택 출력 | PPTX 초안, 체크리스트, 요약본 |

## 4단계: 처리 순서 만들기

이제 실제 절차를 씁니다.

```text
작업회고, 발동조건, 입출력정의를 바탕으로
이 Skill의 처리 순서를 만들어주세요.

처리 순서는 초보자가 봐도 따라갈 수 있게 번호 목록으로 작성해주세요.
각 단계에는 무엇을 확인해야 하는지도 포함해주세요.

결과는 `01_working/처리순서.md`로 저장해주세요.
```

좋은 처리 순서는 이렇게 생겼습니다.

1. 입력 영상 파일이 있는지 확인한다.
2. 영상에 민감정보가 보이는지 먼저 점검한다.
3. 영상 길이와 해상도를 확인한다.
4. 주요 장면을 추출한다.
5. 장면별 사용자 행동을 설명한다.
6. 단계별 매뉴얼 초안을 작성한다.
7. 캡처 없이도 따라갈 수 있게 문장을 보강한다.
8. 결과물을 검수한다.
9. 최종 Markdown과 선택 PPTX를 저장한다.

## 5단계: `SKILL.md` 초안 만들기

준비가 끝났으면 `SKILL.md`를 만듭니다.

```text
지금까지 만든 작업회고, 발동조건, 입출력정의, 처리순서를 바탕으로
`02_output/SKILL.md` 초안을 작성해주세요.

포함할 항목:
- Skill 이름
- 언제 사용하는지
- 사용하면 안 되는 경우
- 필요한 입력자료
- 처리 순서
- 결과물 형식
- 검수 기준
- 사용자에게 확인해야 할 질문

문장은 짧고 명확하게 써주세요.
```

## 6단계: Skill 초안 검수하기

Skill 초안도 검수해야 합니다.

```text
`02_output/SKILL.md`를 검수해주세요.

검수 기준:
1. 언제 써야 하는지 분명한가
2. 필요한 입력자료가 빠지지 않았는가
3. 사용하면 안 되는 자료가 명시되어 있는가
4. 처리 순서가 실제 작업 순서와 맞는가
5. 최종 결과물 형식이 분명한가
6. 검수 기준이 포함되어 있는가
7. 다음에 다른 사람이 읽어도 실행할 수 있는가

문제가 있으면 수정하고, `02_output/검수기준.md`도 함께 만들어주세요.
```

## 7단계: 새 샘플로 다시 실행해 보기

Skill은 한 번 더 써 봐야 합니다.

```text
방금 만든 `02_output/SKILL.md`를 기준으로
새 샘플 입력자료에 적용한다면 어떤 순서로 실행해야 하는지 안내해주세요.

아직 실제 실행은 하지 말고,
재실행 체크리스트를 `02_output/재실행체크리스트.md`로 만들어주세요.
```

재실행이 안 되면 Skill이 아니라 작업 기록에 가깝습니다. Skill은 반복 가능해야 합니다.

## 혼자 해보는 과제

아래 작업 중 하나를 Skill 초안으로 정리해 봅니다.

- 공모전 후보를 엑셀로 정리하는 작업
- 공개자료 폴더를 인벤토리로 정리하는 작업
- 민원답변 누락검토 작업
- HTML 보고서 생성 작업
- PPTX 스타일을 `design.md`로 정리하는 작업

## 오늘 배운 절차

1. 성공한 작업을 고른다.
2. 작업 회고를 먼저 쓴다.
3. 발동 조건을 정한다.
4. 입력자료와 출력자료를 정한다.
5. 처리 순서를 쓴다.
6. `SKILL.md` 초안을 만든다.
7. 새 샘플로 재실행 가능성을 확인한다.

# 08. 기존 PPTX를 읽혀 `design.md` 만들고 새 PPTX 생성하기

## 이 장에서 만들 결과물

이 장에서는 기존 PPTX의 스타일을 분석해 `design.md`로 정리하고, 그 규칙을 바탕으로 새 PPTX 초안을 만듭니다.

최종 결과물은 다음입니다.

- `design.md`: 색상, 폰트, 레이아웃, 문장 규칙을 정리한 디자인 문서
- `샘플_교육자료.pptx`: `design.md`를 바탕으로 만든 새 PPTX
- `PPTX_검수메모.md`: 폰트, 여백, 줄바꿈, 민감정보 여부 검수 기록

이 장의 목표는 PPTX를 예쁘게 꾸미는 것이 아닙니다.

> 기존 PPTX를 감으로 따라 하지 않고,  
> 스타일을 규칙으로 뽑아낸 뒤  
> 새 자료에 재사용하는 방법을 익히는 것입니다.

여기서도 핵심은 완성형 프롬프트가 아닙니다. 처음부터 색상, 폰트, 여백을 모두 알고 말할 필요는 없습니다. 오히려 이렇게 시작합니다.

```text
이 PPTX의 스타일을 참고해서 새 자료를 만들고 싶어.
네가 스타일을 분석하려면 어떤 점을 봐야 해?
표지, 도비라, 본문을 나눠서 먼저 분석 관점을 제안해줘.
```

Codex가 분석 관점을 제안하면, 사용자가 "폰트가 중요하다", "한국어 어절 줄바꿈을 꼭 봐야 한다", "하단 여백이 과하면 안 된다"처럼 기준을 보태는 방식으로 `design.md`를 만듭니다.

## 먼저 알아야 할 것

PPTX 스타일을 참고한다는 것은 내용을 복사하는 일이 아닙니다.

참고해야 할 것은 다음입니다.

- 표지 슬라이드 구조
- 도비라, 즉 장을 나누는 구분 슬라이드 구조
- 본문 슬라이드의 제목 위치
- 본문 텍스트 박스 위치
- 이미지와 설명 문장의 배치
- 색상 팔레트
- 폰트와 굵기
- 강조색
- 여백
- 한국어 줄바꿈 방식

복사하면 안 되는 것은 다음입니다.

- 원본 PPTX의 내부 내용
- 저작권 표시가 필요한 이미지
- 기관 내부자료
- 개인정보
- 발표자 메모나 숨김 슬라이드의 민감 내용

## 준비물

실습 폴더를 만듭니다.

```text
codex-public-practice
└─ 08_PPTX_스타일참조
   ├─ 00_reference
   ├─ 01_working
   └─ 02_output
```

`00_reference` 폴더에 참고할 PPTX를 넣습니다.

직원 실습에서는 공개 가능한 PPTX만 사용합니다. 내부 교육자료를 쓰더라도 외부 배포가 가능한 범위인지 먼저 확인해야 합니다.

이 장의 예시 주제는 다음입니다.

```text
새로 만들 PPTX 주제: 디스코드 화면공유 방법
분량: 4쪽
대상: 사내 직원
목표: 화면공유를 처음 하는 사람도 따라 할 수 있게 안내
```

## 1단계: 바로 PPTX를 만들지 말고 스타일만 분석하기

처음부터 "이 스타일로 PPTX 만들어줘"라고 하면 결과가 흔들립니다. 먼저 스타일 분석 관점을 Codex와 함께 정하고, 그 다음 분석만 시켜야 합니다.

```text
`00_reference` 폴더에 있는 PPTX는 서식 참고용입니다.

내용을 그대로 복사하지 말고,
스타일만 분석해서 `01_working/design.md`로 정리해주세요.

분석할 항목:
- 전체 톤과 용도
- 표지 슬라이드 레이아웃
- 도비라 슬라이드 레이아웃
- 본문 슬라이드 레이아웃
- 제목 위치와 크기
- 본문 위치와 하단 여백
- 이미지 또는 캡처 배치 방식
- 색상 팔레트
- 폰트 이름과 굵기 체계
- 강조색 사용 방식
- 한국어 문장 줄바꿈 규칙

주의:
- 원본 내용을 그대로 옮기지 마세요.
- 저작권 표시, 기관명, 내부 문구는 새 PPTX 규칙에 포함하지 마세요.
- 새 자료에 재사용 가능한 규칙만 정리해주세요.
```

## 2단계: `design.md`에 꼭 들어가야 할 내용

`design.md`가 잘 만들어졌는지 확인합니다.

좋은 `design.md`에는 최소한 아래 내용이 있어야 합니다.

```markdown
# 디자인 규칙

## 1. 전체 톤
- 교육용 실습자료
- 짧고 직접적인 문장
- 파란색 상단 바와 흰 본문 영역

## 2. 슬라이드 유형
- 표지
- 도비라
- 본문
- 요약

## 3. 색상
- 메인 블루: #...
- 강조 노랑: #...
- 본문 글자: #...

## 4. 폰트
- 제목: A2Z 또는 Paperlogy 계열 Bold
- 본문: A2Z 또는 Paperlogy 계열 Regular
- 캡션: 같은 계열 Light

## 5. 한국어 줄바꿈
- 같은 어절 안에서 줄바꿈 금지
- 숫자와 단위는 가능하면 붙여서 유지
- 짧은 문장 중심

## 6. 본문 레이아웃
- 제목은 상단 바 안에 배치
- 본문은 너무 위에 붙이지 않음
- 하단 여백이 과하게 남지 않도록 본문 블록을 아래로 조정
```

내용이 부족하면 "어떤 정보가 부족한지"를 먼저 묻고, 이렇게 다시 보강하게 합니다.

```text
`design.md`가 아직 추상적입니다.
다른 사람이 이 문서만 보고 PPTX를 만들 수 있게
색상값, 폰트 계열, 슬라이드별 레이아웃, 여백 기준, 한국어 줄바꿈 규칙을 더 구체적으로 보강해주세요.
```

## 3단계: 새 PPTX의 구성안 만들기

이제 새 PPTX를 만들기 전에 구성안을 정합니다.

```text
`01_working/design.md`를 참고해서
"디스코드 화면공유 방법" 교육자료 4쪽 구성안을 만들어주세요.

슬라이드 구성:
1. 표지
2. 도비라: 화면공유 시작하기
3. 본문: 서버 또는 음성채널에서 화면공유 시작
4. 본문: 공유 화면 선택과 주의사항

각 슬라이드마다 다음을 적어주세요.
- 슬라이드 제목
- 핵심 문장
- 들어갈 화면 캡처 설명
- 발표자가 말할 포인트
- 한국어 줄바꿈 주의 문장

아직 PPTX 파일은 만들지 말고 구성안만 `01_working/PPTX_구성안.md`로 작성해주세요.
```

캡처가 없어도 괜찮습니다. 캡처 자리에 들어갈 설명을 텍스트로 충분히 써 두면 됩니다.

예:

```text
캡처 자리: 디스코드 음성채널 하단의 화면공유 버튼 위치를 보여주는 이미지
대체 텍스트: 화면공유 버튼은 음성채널에 입장한 뒤 하단 조작 영역에서 찾을 수 있습니다.
```

## 4단계: 새 PPTX 만들기

구성안이 정리되면 PPTX를 생성합니다.

```text
`01_working/design.md`와 `01_working/PPTX_구성안.md`를 기준으로
`02_output/디스코드_화면공유_방법.pptx`를 만들어주세요.

생성 기준:
- 원본 PPTX 내용은 복사하지 마세요.
- copyright 표시는 넣지 마세요.
- 폰트는 A2Z체 계열을 우선 사용하고, 없으면 Paperlogy 계열로 대체해주세요.
- 제목과 본문 굵기 체계는 design.md 기준을 따르세요.
- 같은 어절 안에서 한국어 줄바꿈이 생기지 않게 해주세요.
- 본문 위치는 너무 위에 붙이지 말고, 하단 여백이 과하게 남지 않게 조정해주세요.
- 캡처가 없는 슬라이드는 캡처 자리 설명을 임시 박스로 넣어주세요.
```

PPTX 생성이 어려운 환경이면 먼저 HTML 또는 Markdown 시안으로 만들고, 이후 PPTX로 옮길 수 있습니다.

```text
현재 환경에서 PPTX 생성이 어렵다면
같은 내용으로 슬라이드별 Markdown 시안을 먼저 만들어주세요.
각 슬라이드의 제목, 본문, 캡처 자리, 디자인 지시를 분리해서 적어주세요.
```

## 5단계: 폰트 확인하기

PPTX에서 폰트는 매우 중요합니다. 폰트가 바뀌면 같은 레이아웃도 완전히 다르게 보입니다.

Codex에게 폰트 검수를 시킵니다.

```text
생성한 PPTX의 폰트 적용 상태를 검수해주세요.

확인할 것:
- 제목 폰트
- 본문 폰트
- 캡션 폰트
- 굵기 체계
- 대체 폰트가 섞였는지 여부

검수 결과는 `02_output/PPTX_검수메모.md`에 정리해주세요.
```

직접 PowerPoint를 열 수 있다면 다음도 확인합니다.

1. 슬라이드를 클릭합니다.
2. 제목 텍스트를 선택합니다.
3. 홈 탭의 폰트 이름을 봅니다.
4. 본문 텍스트도 같은 방식으로 확인합니다.
5. PC에 폰트가 없으면 다른 폰트로 대체될 수 있습니다.

## 6단계: 한국어 줄바꿈 확인하기

한국어 PPT에서 중요한 것은 같은 어절 안에서 줄이 갈라지지 않는 것입니다.

나쁜 예:

```text
화면공유를 시
작합니다
```

좋은 예:

```text
화면공유를
시작합니다
```

또는 더 좋은 예:

```text
화면공유를 시작합니다
```

줄바꿈 검수도 Codex에게 먼저 확인 관점을 말하게 할 수 있습니다.

```text
PPTX의 모든 슬라이드 문장을 검토해서
같은 어절 안에서 줄바꿈이 생길 가능성이 있는 문장을 찾아주세요.

수정 기준:
- 긴 문장은 짧은 문장으로 나눕니다.
- 한 줄에 억지로 많이 넣지 않습니다.
- 숫자와 단위, 버튼명은 가능하면 붙여 둡니다.
- 줄바꿈이 필요한 경우 어절 단위로 끊습니다.

수정이 필요하면 PPTX를 다시 고쳐주세요.
```

## 7단계: 여백과 본문 위치 확인하기

본문이 너무 위에 붙거나 아래 여백이 너무 많으면 슬라이드가 비어 보입니다.

검수 대화 예시:

```text
PPTX의 본문 위치와 하단 여백을 검수해주세요.

확인 기준:
- 본문이 상단 제목바에 너무 붙어 있지 않은가
- 하단 여백이 과하게 남지 않는가
- 캡처와 설명 문장이 균형 있게 배치되어 있는가
- 슬라이드마다 본문 시작 위치가 일관적인가

필요하면 본문 블록을 조금 아래로 내리고,
캡처 자리와 설명 문장의 크기를 조정해주세요.
```

## 8단계: 최종 검수표 만들기

```text
최종 PPTX 검수표를 만들어주세요.

검수 항목:
1. 원본 PPTX 내용을 그대로 복사하지 않았는가
2. copyright 표시를 제거했는가
3. 폰트가 지정한 계열로 적용됐는가
4. 한국어 어절 중간 줄바꿈이 없는가
5. 본문 위치와 하단 여백이 적절한가
6. 표지, 도비라, 본문 슬라이드가 구분되는가
7. 캡처가 없는 부분은 임시 박스나 설명으로 표시했는가
8. 민감정보나 내부자료가 들어가지 않았는가

결과는 `02_output/PPTX_검수메모.md`에 표로 저장해주세요.
```

# 09. `/goal`로 메모장 클론 프로젝트 끝까지 밀고 가기

## 이 장에서 만들 결과물

이 장에서는 `/goal` 흐름으로 작은 Windows 메모장 클론을 만들어 봅니다.

최종 결과물은 다음입니다.

- 실행 가능한 메모장 클론 프로그램
- `README.md`: 실행 방법과 기능 설명
- `검증로그.md`: 열기, 저장, 찾기 같은 기능 확인 기록
- `회고.md`: 처음 목표와 실제 결과 비교

이 장은 앞 장보다 어렵습니다. 하지만 직원에게 코딩을 가르치려는 장이 아닙니다.

> 이 장의 목표는 코드를 외우는 것이 아니라,  
> 긴 작업을 목표 단위로 맡기고  
> 실행, 검증, 수정까지 이어가는 감각을 익히는 것입니다.

`/goal`도 완성된 명세서를 한 번에 넣는 기능으로 이해하면 안 됩니다. 목표를 열고, Codex가 질문하게 하고, 사용자가 답하면서 범위를 줄여가는 방식입니다.

```text
작은 메모장 앱을 만들어보고 싶은데,
목표를 잡기 전에 네가 나에게 확인해야 할 질문을 먼저 해줘.
오늘 안에 끝내려면 어떤 기능을 빼야 할지도 제안해줘.
```

처음 말은 거칠어도 됩니다. 중요한 것은 목표를 잡은 뒤 구현, 실행, 오류 수정, 검증까지 대화를 이어가는 것입니다.

## 왜 메모장 클론인가요

메모장은 누구나 압니다. 그래서 결과가 맞는지 판단하기 쉽습니다.

좋은 실습 프로젝트는 다음 조건을 만족해야 합니다.

- 결과물이 눈에 보인다.
- 성공과 실패를 판단하기 쉽다.
- 기능 범위를 줄일 수 있다.
- 실행해 보고 바로 수정 요청을 할 수 있다.
- 복잡해 보이지만 작은 버전으로 만들 수 있다.

메모장 클론은 이 조건에 잘 맞습니다.

## 먼저 범위를 줄입니다

처음부터 Windows 기본 메모장을 모두 따라 만들려고 하면 어렵습니다.

이 장의 최소 기능은 다음입니다.

| 기능 | 이번 실습 포함 여부 |
| --- | --- |
| 새 문서 | 포함 |
| 파일 열기 | 포함 |
| 저장 | 포함 |
| 다른 이름으로 저장 | 포함 |
| 찾기 | 포함 |
| 글자 크기 조정 | 포함 |
| 탭 기능 | 선택 |
| 자동 저장 | 선택 |
| 인쇄 | 제외 |
| 복잡한 설정 화면 | 제외 |

처음 목표는 작아야 합니다. 작게 완성한 뒤 늘리는 것이 좋습니다.

## 준비물

실습 폴더를 만듭니다.

```text
codex-public-practice
└─ 09_goal_메모장_클론
   ├─ 00_reference
   ├─ 01_working
   ├─ 02_output
   └─ app
```

`00_reference` 폴더에는 참고자료를 둘 수 있습니다.

- Windows 기본 메모장을 열어 보고 기능 목록을 적은 메모
- 원하는 기능 목록
- 제외할 기능 목록

실제 코드는 Codex가 만들게 합니다.

## 1단계: `/goal` 시작하기

Codex에서 목표를 시작합니다. 사용 환경에 따라 `/goal` 명령을 직접 입력하거나, 목표 기반 작업으로 요청할 수 있습니다. 아래 예시는 완성된 명세서가 아니라 첫 목표를 여는 말입니다.

```text
/goal
Windows에서 실행되는 아주 작은 메모장 클론을 만들고 싶습니다.

목표:
- 실행파일을 더블클릭하면 메모장처럼 창이 열려야 합니다.
- 새 문서, 파일 열기, 저장, 다른 이름으로 저장이 되어야 합니다.
- 찾기 기능과 글자 크기 조정 기능이 있으면 좋겠습니다.
- 처음부터 완벽한 메모장이 아니라 최소 기능이 동작하면 됩니다.

진행 방식:
1. 현재 PC에서 사용할 수 있는 개발 도구를 먼저 확인해주세요.
2. 가능한 구현 방식을 제안해주세요.
3. 이번 실습에서 포함할 기능과 제외할 기능을 표로 정리해주세요.
4. 제가 확인하면 구현, 빌드, 실행 확인, 오류 수정까지 진행해주세요.
5. 최종적으로 실행파일 위치, 사용법, 검증 결과를 정리해주세요.
```

중요한 것은 "코드 짜줘"가 아닙니다. 목표, 범위, 검증까지 한 번에 맡기는 것입니다.

## 2단계: 개발 도구 확인시키기

PC마다 설치된 도구가 다릅니다. 그래서 먼저 현재 환경을 확인해야 합니다.

Codex가 직접 확인할 수 있다면 확인하게 하고, 그렇지 않다면 사용자가 결과를 알려줍니다.

대화 시작문:

```text
현재 PC에서 이 프로젝트를 만들 수 있는 도구를 확인해주세요.

확인할 것:
- .NET SDK 또는 .NET Framework 사용 가능 여부
- Node.js 사용 가능 여부
- Python 사용 가능 여부
- PowerShell 사용 가능 여부
- 실행파일을 만들 수 있는 방법

확인 결과를 바탕으로 초보 직원 실습에 가장 단순한 구현 방식을 추천해주세요.
```

가능한 방식은 여러 가지입니다.

| 방식 | 장점 | 주의점 |
| --- | --- | --- |
| .NET WinForms | Windows 앱 느낌이 자연스러움 | 개발 도구 확인 필요 |
| Electron | 웹기술로 데스크톱 앱 가능 | 설치 용량이 큼 |
| Python Tkinter | 간단히 만들기 쉬움 | 실행파일 패키징 추가 필요 |
| HTML 파일 | 가장 쉬움 | 네이티브 앱 느낌은 약함 |

이 장의 목적은 완벽한 기술 선택이 아니라 "현재 PC에서 끝까지 되는 방법"을 찾는 것입니다.

## 3단계: 기능 범위 확정하기

도구 확인 후 기능 범위를 확정합니다.

```text
이번 실습의 기능 범위를 확정해주세요.

반드시 포함:
- 새 문서
- 파일 열기
- 저장
- 다른 이름으로 저장
- 찾기
- 글자 크기 키우기/줄이기

이번에는 제외:
- 탭 기능
- 자동 저장
- 인쇄
- 복잡한 설정 화면

결과를 `01_working/기능범위.md`로 정리해주세요.
각 기능마다 "완성 판단 기준"을 적어주세요.
```

완성 판단 기준은 이렇게 써야 합니다.

| 기능 | 완성 판단 기준 |
| --- | --- |
| 파일 열기 | `.txt` 파일을 선택하면 내용이 편집창에 표시된다 |
| 저장 | 기존 파일 경로가 있으면 같은 파일에 저장된다 |
| 다른 이름 저장 | 파일 저장 창이 열리고 새 경로에 저장된다 |
| 찾기 | 검색어를 입력하면 해당 단어 위치로 이동한다 |
| 글자 크기 | 버튼 또는 메뉴로 편집창 글자 크기가 바뀐다 |

## 4단계: 구현 맡기기

범위가 확정되면 구현을 맡깁니다.

```text
`01_working/기능범위.md` 기준으로 메모장 클론을 구현해주세요.

요구사항:
- 소스코드는 `app` 폴더에 정리해주세요.
- 빌드 방법을 함께 만들어주세요.
- 실행파일이 만들어지면 `02_output` 폴더로 복사해주세요.
- 구현 후 바로 실행 확인까지 해주세요.
- 오류가 나면 오류 메시지를 읽고 수정해주세요.

완료 후 알려줄 것:
- 만든 파일 목록
- 실행 방법
- 구현한 기능
- 아직 구현하지 않은 기능
- 테스트한 결과
```

직원은 이 과정에서 코드를 다 이해할 필요가 없습니다. 대신 결과물이 실제로 실행되는지 봐야 합니다.

## 5단계: 실행해 보기

실행파일이 만들어지면 더블클릭해 봅니다.

확인할 것:

1. 창이 열리는가
2. 글자를 입력할 수 있는가
3. 새 파일로 초기화할 수 있는가
4. 파일을 저장할 수 있는가
5. 저장한 파일을 다시 열 수 있는가
6. 찾기 기능이 동작하는가
7. 글자 크기가 바뀌는가

실행이 안 되면 이렇게 말합니다.

```text
실행파일을 더블클릭했는데 창이 열리지 않습니다.
가능한 원인을 확인하고, 실행 로그 또는 오류 메시지를 바탕으로 수정해주세요.
```

기능이 일부만 되면 이렇게 말합니다.

```text
앱은 실행되지만 저장 기능이 예상대로 동작하지 않습니다.
새 파일을 작성한 뒤 저장하고, 다시 열어서 내용이 유지되는지 확인하는 테스트를 해주세요.
문제가 있으면 수정해주세요.
```

## 6단계: 검증로그 만들기

프로그램은 "만들었다"보다 "검증했다"가 중요합니다.

```text
메모장 클론의 기능 검증로그를 만들어주세요.

검증 항목:
1. 앱 실행
2. 새 문서
3. 파일 열기
4. 저장
5. 다른 이름으로 저장
6. 찾기
7. 글자 크기 조정
8. 종료 후 다시 실행

각 항목은 통과/실패/확인필요로 표시하고,
실패한 항목은 재현 방법과 수정 여부를 적어주세요.

결과는 `02_output/검증로그.md`로 저장해주세요.
```

## 7단계: README 만들기

다른 사람이 실행하려면 설명서가 필요합니다.

```text
최종 결과물용 `02_output/README.md`를 만들어주세요.

포함할 내용:
- 이 프로그램이 무엇인지
- 실행 방법
- 지원하는 기능
- 저장되는 파일 형식
- 알려진 제한사항
- 다시 빌드하는 방법
- 문제 발생 시 확인할 것

직원 교육용으로 어렵지 않게 써주세요.
```

## 8단계: 회고 작성하기

```text
이번 `/goal` 프로젝트 회고를 `02_output/회고.md`로 작성해주세요.

포함할 내용:
- 처음 목표
- 실제 완성된 결과
- 줄인 기능

- Codex에게 다시 지시해서 고친 부분

- 이 작업을 Skill로 남긴다면 들어가야 할 절차
```

# 10. Codex로 서버/API 설정 관리하기: Instagram·Threads 분석

## 이 장에서 만들 결과물

이 장에서는 Instagram이나 Threads의 반응 추이를 API로 분석할 수 있는지 확인하고, 가능하면 테스트 설정까지 해 봅니다.

최종 결과물은 다음 정도입니다.

- `meta_api_가능여부.md`: API로 볼 수 있는 지표와 못 보는 지표 정리
- `.env.example`: 토큰과 앱 정보가 들어갈 자리만 적은 예시 파일
- `api_test_log.md`: 테스트하다가 성공하거나 막힌 기록
- `instagram_threads_분석.html`: 게시글 반응과 추이를 정리한 샘플 보고서
- `다음번_세팅메모.md`: 다음에 다시 할 때 볼 메모

이 장은 04장 Browser Use/Playwright와 같은 계열입니다. 개발자센터 화면을 같이 보고, 공식 문서를 확인하고, 오류 메시지를 읽는 일이기 때문입니다.

다만 입문 장에서 바로 하기에는 어렵습니다. 로그인, 개발자 계정, 토큰, 앱 권한이 나오기 때문입니다. 그래서 04장에서는 맛보기로만 보고, 여기서 심화 실습으로 따로 다룹니다.

## 잘 쓴 프롬프트가 아니라 대화로 시작합니다

사용자가 처음부터 이렇게 잘 정리해서 말할 필요는 없습니다.

```text
인스타그램 반응 추이 같은 거 분석할 수 있나?
```

이 정도면 됩니다.

그러면 Codex가 바로 코드를 짜는 게 아니라 먼저 되물어야 합니다.

```text
가능한지부터 확인해보겠습니다.
Instagram만 볼까요, Threads도 같이 볼까요?
보고 싶은 건 게시글별 반응인가요, 계정 전체 추이인가요?
본인 계정 또는 권한 있는 계정 기준으로 봐도 될까요?
```

사용자는 대충 답해도 됩니다.

```text
일단 메타에서 확인할 수 있는 지표가 뭐가 있는지 네가 보고 설명해줘.
그럼 내가 골라볼게.
```

이 흐름이 핵심입니다. 사용자가 완성형 요청문을 쓰는 것이 아니라, Codex가 필요한 질문을 하고 사용자가 하나씩 고르는 방식입니다.

## 실제 대화 예시

아래처럼 짧게 주고받으면 됩니다.

**사용자**

```text
내 인스타나 스레드 글 반응을 좀 분석해보고 싶은데,
Meta API로 가능한지 봐줄래?
```

**Codex**

```text
먼저 가능한 지표를 확인해볼게요.
Instagram과 Threads 중 어디를 우선 볼까요?
```

**사용자**

```text
둘 다 가능하면 좋은데, 네가 봤을 때 쉬운 것부터.
```

**Codex**

```text
그럼 공식 문서 기준으로
1. Threads에서 가능한 지표
2. Instagram에서 가능한 지표
3. 권한이나 계정 조건
4. API로 안 되는 것
을 먼저 정리해볼게요.
```

**사용자**

```text
그래. 근데 어려운 말 말고,
내가 고를 수 있게 표로 설명해줘.
```

이런 식으로 대화가 이어집니다.

## 먼저 "무엇을 볼 수 있는지"부터 확인합니다

처음 산출물은 설정 파일이 아닙니다. 가능 여부 표입니다.

Codex에게는 이렇게 말하면 됩니다.

```text
메타에서 확인할 수 있는 지표가 어떤 게 있는지 네가 보고 설명해줘.
내가 그중에서 골라볼게.
```

Codex는 공식 문서를 확인해서 아래처럼 정리해야 합니다.

| 구분 | 볼 수 있을 수 있는 것 | 조건 | 내가 고를지 |
| --- | --- | --- | --- |
| Threads 게시글 | 조회수, 좋아요, 답글, 리포스트, 인용 | 본인 또는 권한 있는 계정, 토큰 필요 |  |
| Instagram 게시글 | 도달, 조회, 반응 등 인사이트 | 계정 유형과 권한 조건 확인 필요 |  |
| 계정 전체 추이 | 기간별 변화 일부 | API 제공 범위 확인 필요 |  |
| 남의 계정 상세 분석 | 공식 권한 없이는 불가 | 우회 수집 금지 | 제외 |

여기서 사용자가 고릅니다.

```text
Threads 게시글별 조회수랑 좋아요, 답글 정도면 충분할 것 같아.
그걸 먼저 테스트해보자.
```

또는 이렇게 말할 수도 있습니다.

```text
인스타는 조건이 복잡해 보이니까 일단 보류하고,
스레드부터 해보자.
```

이렇게 고른 뒤에야 세팅으로 넘어갑니다.

## 그다음 개발자센터를 같이 봅니다

가능한 지표를 골랐으면 그때 Meta 개발자센터를 봅니다.

사용자가 이렇게 말합니다.

```text
그럼 개발자센터 켜서 같이 보자.
내가 로그인할 테니까 너는 어디를 봐야 하는지 알려줘.
```

Codex는 이렇게 안내해야 합니다.

```text
좋습니다. 저는 다음 항목만 확인하겠습니다.
- 앱이 있는지
- Threads 또는 Instagram 관련 제품을 추가할 수 있는지
- 토큰을 어디서 발급하는지
- 필요한 권한 이름이 무엇인지
- 테스트 호출을 할 수 있는지

로그인, 2단계 인증, 토큰 확인은 사용자가 직접 진행하세요.
토큰이나 App Secret은 저에게 붙여넣지 마세요.
```

Browser Use는 이런 순간에 씁니다. 화면을 함께 보고 "여기서 뭘 눌러야 하는지"를 설명하게 합니다.

Playwright는 반복 확인이 필요할 때 씁니다. 예를 들어 테스트 호출을 여러 번 하고, 결과 JSON을 저장하고, HTML 보고서를 다시 만드는 흐름이면 Playwright나 스크립트가 유용합니다.

Chrome 확장은 꼭 필요할 때만 씁니다. 보통은 개발자센터 화면 확인, 공식 문서 확인, 로컬 테스트 파일 작성만으로 충분합니다.

## 비밀값은 사람이 넣고, Codex는 빈 양식만 만듭니다

API 설정에서 가장 중요한 안전선은 이것입니다.

> 토큰과 App Secret은 Codex에게 보여주지 않습니다.

Codex에게는 이렇게 말합니다.

```text
실제 값은 내가 넣을게.
너는 어떤 값이 필요한지 빈 양식만 만들어줘.
```

그러면 `.env.example`은 이 정도면 됩니다.

```env
META_ACCESS_TOKEN=여기에_직접_입력
META_APP_ID=여기에_직접_입력
META_APP_SECRET=여기에_직접_입력
THREADS_USER_ID=여기에_직접_입력
INSTAGRAM_USER_ID=여기에_직접_입력
```

사용자가 실제 값을 `.env`에 직접 넣습니다. 교재나 캡처에는 `.env.example`만 보여줍니다.

## 작은 테스트부터 합니다

이제 바로 분석 보고서를 만들지 않습니다. 먼저 API가 응답하는지 봅니다.

사용자는 이렇게 말하면 됩니다.

```text
일단 되는지만 보자.
토큰이랑 계정 ID가 맞는지 작은 테스트부터 해줘.
```

성공하면 Codex가 응답 JSON을 저장합니다.

실패하면 사용자는 오류를 붙잡고 이렇게 말합니다.

```text
이게 뭔 오류야?
토큰 문제야, 권한 문제야, 계정 ID 문제야?
내가 어디를 확인하면 돼?
```

Codex는 오류를 표로 정리합니다.

| 오류 | 쉬운 해석 | 확인할 곳 |
| --- | --- | --- |
| 토큰 만료 | 로그인 권한이 오래되었거나 잘못된 토큰 | 토큰 발급 화면 |
| 권한 부족 | 필요한 API 권한이 없음 | 앱 권한, 앱 모드 |
| ID 오류 | 계정 ID나 게시글 ID가 다름 | 테스트 응답의 ID |
| API 경로 오류 | Instagram/Threads 엔드포인트를 혼동 | 공식 문서 |

실패는 나쁜 게 아닙니다. 다음에 덜 헤매게 해주는 기록입니다.

## 마지막에 분석 보고서로 만듭니다

테스트가 성공하면 그때 원래 목적을 합니다.

```text
이제 받은 데이터로 보기 좋은 HTML 만들어줘.
게시글별 조회수, 좋아요, 답글, 리포스트, 인용을 표로 보여주고,
반응이 높은 글 순서도 뽑아줘.
예전 백업이 있으면 이번 백업이랑 비교해서 증가분도 봐줘.
```

예전에 Threads 분석을 했을 때도 흐름은 이랬습니다.

1. Threads API 토큰을 준비한다.
2. 게시글 목록과 인사이트를 백업한다.
3. 조회수, 좋아요, 답글, 리포스트, 인용을 표로 만든다.
4. 이전 백업과 비교해 증가분을 본다.
5. 잘 먹힌 글의 주제와 형식을 해석한다.

즉 이 장의 목표는 "Meta API 배우기"가 아닙니다.

> 내가 궁금한 반응 추이를 보기 위해  
> Codex가 개발자센터, 공식 문서, 테스트 호출, 결과 정리를  
> 옆에서 같이 처리하게 하는 경험입니다.

## 안전선

이것만은 지킵니다.

- Access Token, App Secret, 비밀번호는 채팅창이나 교재에 붙여넣지 않습니다.
- 기관 공식 계정은 권한을 받은 경우에만 다룹니다.
- 남의 계정 데이터를 우회해서 수집하지 않습니다.
- 삭제, 운영 전환, 권한 신청, 결제 버튼은 사람이 직접 판단합니다.
- 캡처에는 토큰, 시크릿, 내부 앱 이름, 개인 계정 정보가 보이지 않게 합니다.

## 오늘 배운 절차

1. 짧게 말한다. "이거 API로 가능한지 봐줘."
2. Codex가 필요한 질문을 하게 둔다.
3. 볼 수 있는 지표를 Codex가 표로 설명한다.
4. 사용자가 그중에서 고른다.
5. 개발자센터 화면은 Browser Use로 같이 본다.
6. 반복 테스트가 필요하면 Playwright나 스크립트를 쓴다.
7. 비밀값은 사용자가 직접 넣는다.
8. 작은 테스트가 성공하면 분석 HTML을 만든다.
9. 다음번 세팅 메모를 남긴다.
