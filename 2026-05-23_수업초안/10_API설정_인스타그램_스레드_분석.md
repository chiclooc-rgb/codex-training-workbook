# 10. Codex로 서버/API 설정 관리하기: Instagram·Threads 분석

## 이 장에서 만들 결과물

이 장에서는 Instagram이나 Threads의 반응 추이를 API로 분석할 수 있는지 확인하고, 가능하면 테스트 설정까지 해 봅니다.

최종 결과물은 다음 정도입니다.

- `meta_api_가능여부.md`: API로 볼 수 있는 지표와 못 보는 지표 정리
- `.env.example`: 토큰과 앱 정보가 들어갈 자리만 적은 예시 파일
- `api_test_log.md`: 테스트하다가 성공하거나 막힌 기록
- `instagram_threads_분석.html`: 게시글 반응과 추이를 정리한 샘플 보고서
- `다음번_세팅메모.md`: 다음에 다시 할 때 볼 메모

이 장은 04장 Browser Use/Playwright와 같은 계열입니다. 개발자센터 화면을 같이 보고, 공식 문서를 확인하고, 오류 메시지를 읽는 일이기 때문입니다.

다만 입문 장에서 바로 하기에는 어렵습니다. 로그인, 개발자 계정, 토큰, 앱 권한이 나오기 때문입니다. 그래서 04장에서는 맛보기로만 보고, 여기서 심화 실습으로 따로 다룹니다.

## 잘 쓴 프롬프트가 아니라 대화로 시작합니다

사용자가 처음부터 이렇게 잘 정리해서 말할 필요는 없습니다.

```text
인스타그램 반응 추이 같은 거 분석할 수 있나?
```

이 정도면 됩니다.

그러면 Codex가 바로 코드를 짜는 게 아니라 먼저 되물어야 합니다.

```text
가능한지부터 확인해보겠습니다.
Instagram만 볼까요, Threads도 같이 볼까요?
보고 싶은 건 게시글별 반응인가요, 계정 전체 추이인가요?
본인 계정 또는 권한 있는 계정 기준으로 봐도 될까요?
```

사용자는 대충 답해도 됩니다.

```text
일단 메타에서 확인할 수 있는 지표가 뭐가 있는지 네가 보고 설명해줘.
그럼 내가 골라볼게.
```

이 흐름이 핵심입니다. 사용자가 완성형 요청문을 쓰는 것이 아니라, Codex가 필요한 질문을 하고 사용자가 하나씩 고르는 방식입니다.

## 실제 대화 예시

아래처럼 짧게 주고받으면 됩니다.

**사용자**

```text
내 인스타나 스레드 글 반응을 좀 분석해보고 싶은데,
Meta API로 가능한지 봐줄래?
```

**Codex**

```text
먼저 가능한 지표를 확인해볼게요.
Instagram과 Threads 중 어디를 우선 볼까요?
```

**사용자**

```text
둘 다 가능하면 좋은데, 네가 봤을 때 쉬운 것부터.
```

**Codex**

```text
그럼 공식 문서 기준으로
1. Threads에서 가능한 지표
2. Instagram에서 가능한 지표
3. 권한이나 계정 조건
4. API로 안 되는 것
을 먼저 정리해볼게요.
```

**사용자**

```text
그래. 근데 어려운 말 말고,
내가 고를 수 있게 표로 설명해줘.
```

이런 식으로 대화가 이어집니다.

## 먼저 "무엇을 볼 수 있는지"부터 확인합니다

처음 산출물은 설정 파일이 아닙니다. 가능 여부 표입니다.

Codex에게는 이렇게 말하면 됩니다.

```text
메타에서 확인할 수 있는 지표가 어떤 게 있는지 네가 보고 설명해줘.
내가 그중에서 골라볼게.
```

Codex는 공식 문서를 확인해서 아래처럼 정리해야 합니다.

| 구분 | 볼 수 있을 수 있는 것 | 조건 | 내가 고를지 |
| --- | --- | --- | --- |
| Threads 게시글 | 조회수, 좋아요, 답글, 리포스트, 인용 | 본인 또는 권한 있는 계정, 토큰 필요 |  |
| Instagram 게시글 | 도달, 조회, 반응 등 인사이트 | 계정 유형과 권한 조건 확인 필요 |  |
| 계정 전체 추이 | 기간별 변화 일부 | API 제공 범위 확인 필요 |  |
| 남의 계정 상세 분석 | 공식 권한 없이는 불가 | 우회 수집 금지 | 제외 |

여기서 사용자가 고릅니다.

```text
Threads 게시글별 조회수랑 좋아요, 답글 정도면 충분할 것 같아.
그걸 먼저 테스트해보자.
```

또는 이렇게 말할 수도 있습니다.

```text
인스타는 조건이 복잡해 보이니까 일단 보류하고,
스레드부터 해보자.
```

이렇게 고른 뒤에야 세팅으로 넘어갑니다.

## 그다음 개발자센터를 같이 봅니다

가능한 지표를 골랐으면 그때 Meta 개발자센터를 봅니다.

사용자가 이렇게 말합니다.

```text
그럼 개발자센터 켜서 같이 보자.
내가 로그인할 테니까 너는 어디를 봐야 하는지 알려줘.
```

Codex는 이렇게 안내해야 합니다.

```text
좋습니다. 저는 다음 항목만 확인하겠습니다.
- 앱이 있는지
- Threads 또는 Instagram 관련 제품을 추가할 수 있는지
- 토큰을 어디서 발급하는지
- 필요한 권한 이름이 무엇인지
- 테스트 호출을 할 수 있는지

로그인, 2단계 인증, 토큰 확인은 사용자가 직접 진행하세요.
토큰이나 App Secret은 저에게 붙여넣지 마세요.
```

Browser Use는 이런 순간에 씁니다. 화면을 함께 보고 "여기서 뭘 눌러야 하는지"를 설명하게 합니다.

Playwright는 반복 확인이 필요할 때 씁니다. 예를 들어 테스트 호출을 여러 번 하고, 결과 JSON을 저장하고, HTML 보고서를 다시 만드는 흐름이면 Playwright나 스크립트가 유용합니다.

Chrome 확장은 꼭 필요할 때만 씁니다. 보통은 개발자센터 화면 확인, 공식 문서 확인, 로컬 테스트 파일 작성만으로 충분합니다.

## 비밀값은 사람이 넣고, Codex는 빈 양식만 만듭니다

API 설정에서 가장 중요한 안전선은 이것입니다.

> 토큰과 App Secret은 Codex에게 보여주지 않습니다.

Codex에게는 이렇게 말합니다.

```text
실제 값은 내가 넣을게.
너는 어떤 값이 필요한지 빈 양식만 만들어줘.
```

그러면 `.env.example`은 이 정도면 됩니다.

```env
META_ACCESS_TOKEN=여기에_직접_입력
META_APP_ID=여기에_직접_입력
META_APP_SECRET=여기에_직접_입력
THREADS_USER_ID=여기에_직접_입력
INSTAGRAM_USER_ID=여기에_직접_입력
```

사용자가 실제 값을 `.env`에 직접 넣습니다. 교재나 캡처에는 `.env.example`만 보여줍니다.

## 작은 테스트부터 합니다

이제 바로 분석 보고서를 만들지 않습니다. 먼저 API가 응답하는지 봅니다.

사용자는 이렇게 말하면 됩니다.

```text
일단 되는지만 보자.
토큰이랑 계정 ID가 맞는지 작은 테스트부터 해줘.
```

성공하면 Codex가 응답 JSON을 저장합니다.

실패하면 사용자는 오류를 붙잡고 이렇게 말합니다.

```text
이게 뭔 오류야?
토큰 문제야, 권한 문제야, 계정 ID 문제야?
내가 어디를 확인하면 돼?
```

Codex는 오류를 표로 정리합니다.

| 오류 | 쉬운 해석 | 확인할 곳 |
| --- | --- | --- |
| 토큰 만료 | 로그인 권한이 오래되었거나 잘못된 토큰 | 토큰 발급 화면 |
| 권한 부족 | 필요한 API 권한이 없음 | 앱 권한, 앱 모드 |
| ID 오류 | 계정 ID나 게시글 ID가 다름 | 테스트 응답의 ID |
| API 경로 오류 | Instagram/Threads 엔드포인트를 혼동 | 공식 문서 |

실패는 나쁜 게 아닙니다. 다음에 덜 헤매게 해주는 기록입니다.

## 마지막에 분석 보고서로 만듭니다

테스트가 성공하면 그때 원래 목적을 합니다.

```text
이제 받은 데이터로 보기 좋은 HTML 만들어줘.
게시글별 조회수, 좋아요, 답글, 리포스트, 인용을 표로 보여주고,
반응이 높은 글 순서도 뽑아줘.
예전 백업이 있으면 이번 백업이랑 비교해서 증가분도 봐줘.
```

예전에 Threads 분석을 했을 때도 흐름은 이랬습니다.

1. Threads API 토큰을 준비한다.
2. 게시글 목록과 인사이트를 백업한다.
3. 조회수, 좋아요, 답글, 리포스트, 인용을 표로 만든다.
4. 이전 백업과 비교해 증가분을 본다.
5. 잘 먹힌 글의 주제와 형식을 해석한다.

즉 이 장의 목표는 "Meta API 배우기"가 아닙니다.

> 내가 궁금한 반응 추이를 보기 위해  
> Codex가 개발자센터, 공식 문서, 테스트 호출, 결과 정리를  
> 옆에서 같이 처리하게 하는 경험입니다.

## 안전선

이것만은 지킵니다.

- Access Token, App Secret, 비밀번호는 채팅창이나 교재에 붙여넣지 않습니다.
- 기관 공식 계정은 권한을 받은 경우에만 다룹니다.
- 남의 계정 데이터를 우회해서 수집하지 않습니다.
- 삭제, 운영 전환, 권한 신청, 결제 버튼은 사람이 직접 판단합니다.
- 캡처에는 토큰, 시크릿, 내부 앱 이름, 개인 계정 정보가 보이지 않게 합니다.

## 오늘 배운 절차

1. 짧게 말한다. "이거 API로 가능한지 봐줘."
2. Codex가 필요한 질문을 하게 둔다.
3. 볼 수 있는 지표를 Codex가 표로 설명한다.
4. 사용자가 그중에서 고른다.
5. 개발자센터 화면은 Browser Use로 같이 본다.
6. 반복 테스트가 필요하면 Playwright나 스크립트를 쓴다.
7. 비밀값은 사용자가 직접 넣는다.
8. 작은 테스트가 성공하면 분석 HTML을 만든다.
9. 다음번 세팅 메모를 남긴다.
